# The Timone Process

> The single written definition of the engineering process Timone enforces on every managed project. Stage skills implement this document; when a skill and this spec disagree, the spec wins and the skill gets fixed.
> Delivered by phase-01 for [PRD-01.R1](doc/specs/prd/prd-01-process-layer.criteria.md).

## Stages at a glance

| # | Stage | Owning skill | Artifact produced | Closing gate |
|---|-------|--------------|-------------------|--------------|
| 0 | Onboarding *(cross-cutting, once per project)* | `timone-onboard` | Manifest entry + project doc tree + `doc/specs/product-overview.md` (incl. constraints) + founding ADRs (stack) + `doc/standards.md` | Human confirms the product overview **and** the standards |
| 1 | Triage | `timone-triage` | Classification record: kind (feature / bug / chore / question) + process entry point + rationale | Classification recorded on the request |
| 2 | Requirements discovery | `timone-grill` (one session) / `timone-wayfind` (at scale) | Resolved decision tree + inline glossary updates (`CONTEXT.md`); at scale, additionally a wayfinder map of decision tickets | All branches resolved; summary accepted by the human — at scale: frontier empty, fog cleared, destination artifact committed |
| 3 | Requirements | `timone-prd` | PRD pair: `doc/specs/prd/prd-NN-<slug>.md` + `.criteria.md` | Human approves the requirement list **before** files are written; PRD becomes Active |
| 4 | Architecture | `timone-adr` | `doc/adr/NNNN-<slug>.md` — standalone, written **at decision time** | ADR status `accepted` |
| 5 | Planning | `timone-plan` | Phase file: `doc/plans/phases/phase-NN.md` with vertical-slice sub-phases | Human approves the breakdown; no undocumented significant decision (else → stage 4 first) |
| 6 | Implementation | `timone-execute` | Code on a work branch + sub-agent handoffs + completion report | Every sub-phase's validation steps pass |
| 7 | Verification | `timone-verify` | Verification report: `doc/plans/phases/reports/phase-NN-verification.md` + updated criteria statuses | All MUST criteria PASS or HUMAN-CHECK, zero regressions, within 2 verify-fix loops |
| 8 | Delivery | `timone-deliver` | Delivery report: `doc/plans/phases/reports/phase-NN-delivery.md` (both review axes) + a pull request referencing the driving ticket, carrying the verification outcome | PR open with passing checks; merge stays human |
| 9 | Feedback | `timone-improve` | Feedback record: `doc/feedback/NNN-<slug>.md` (per-item triage + decisions + dispatch trace) + PRD and record amendments | Human confirms, declines or defers each item before anything moves |
| 10 | Deployment *(stage defined — skill post-MVP)* | `timone-deploy` | Release to a target environment + deploy record | Environment-specific checks green |
| 11 | Maintenance *(stage defined — skill post-MVP)* | `timone-maintain` | Dependency-update and production-issue intake feeding stage 1 | Each intake item triaged |

## Stage notes

**0 — Onboarding.** Registers a repo in `timone.yaml` (repo URL, path under `projects/`, stack, platform bindings), creates the artifact tree (`doc/specs/`, `doc/specs/prd/`, `doc/adr/`, `doc/plans/phases/`), and drafts the one-page product overview — problem, users, goals, success definition, non-goals, **and constraints** (client policies, hosting, compliance, budget). Stack choices are recorded as **founding ADRs**, never restated elsewhere. Onboarding also produces `doc/standards.md` — deliberately thin: which entries of Timone's central standards library apply, plus project-specific deviations; anything a tool can enforce lives in tool config, not prose. For an **existing** codebase, conventions are *observed* from the code, not imposed — conflicts with preferred standards are flagged for an explicit decision. Gate: human confirms the overview and the standards.

**1 — Triage.** Every incoming request enters here. Routing: feature → stage 2 (or 3 if requirements are already clear; when the request spans multiple independent unresolved decision areas, triage *recommends* stage 2's at-scale mode, `timone-wayfind` — the human decides); bug or post-delivery observation → stage 9; chore/technical enabler → stage 5, unanchored (see PRD anchoring below); question → answered, no pipeline. **Recording:** the classification (kind + entry point + one-paragraph rationale) is recorded on the request itself. When the request is a GitHub issue and the project's repo is GitHub-hosted, the record is an issue comment plus a `triage:<kind>` label (via `gh`). Otherwise — free-form request, or non-GitHub remote — it is persisted as `doc/triage/NNN-<slug>.md` in the target project (NNN zero-padded, allocated by scanning existing records) and committed; the fallback is always explicit, never a silent skip.

**2 — Requirements discovery.** Relentless interview: one question at a time, each with a recommended answer; anything answerable from the codebase is answered from the codebase, not asked. Ends with a summary of decisions and risks. Its conclusions are raw material for stage 3 — they evaporate unless persisted. The interview also maintains the project's **domain glossary** (`CONTEXT.md`, created lazily, glossary only — no implementation details): fuzzy terms are sharpened into canonical ones, conflicts with the existing glossary are challenged on the spot, and resolved terms are written down immediately.

**At scale — `timone-wayfind`.** When discovery exceeds one session — multiple independent decision areas, research needed between conversations, decisions blocking other decisions — stage 2 runs as **wayfinding** (adapted from Matt Pocock's wayfinder; [ADR-0010](doc/adr/0010-wayfinder-discovery-maps.md)): the idea is charted as a **map**, a single issue on the project's tracker labelled `wayfinder:map`, whose child issues are **decision tickets** — questions whose resolution is a decision, never slices of a build — each sized to one session and typed `research` (agent-alone), `grilling` (with the human — the default; the interview discipline above, glossary maintenance included), `prototype` (with the human — a cheap, throwaway artifact to react to when "how should it look/behave" is the key question; built via `timone-prototype` under the convention of [ADR-0011](doc/adr/0011-prototype-convention.md)) or `task` (manual work that unblocks a decision, never a deliverable — anything that is a build routes through stage 1 like any other request). Charting names the **destination** first, tickets what is already sharp, and writes the rest as fog (**Not yet specified**); working sessions claim one frontier ticket (open, unblocked, unassigned), resolve it, record the resolution on the ticket, and graduate whatever fog the answer sharpened — **one ticket per session**, `research` excepted. **The map is scaffolding, never spec:** nothing on it is normative — a resolution passing stage 4's significance test becomes an ADR at decision time, the destination lands in-repo (normally the stage-3 PRD pair), and PRDs and ADRs restate what they need rather than point into tickets, keeping ADR-0006 intact. A project whose repo is not GitHub-hosted falls back — loudly, as in stage 1 — to a committed markdown map under `doc/wayfinder/`. The map closes only after the destination artifact is committed, its closing comment linking it.

**3 — Requirements.** The PRD pair is the **single source of truth** for what is being built (ADR-0006): a stakeholder-readable narrative free of test machinery, and a formal criteria register. Tickets scope work and point here; they never hold requirement detail. PRDs covering user-facing functionality include accessibility acceptance criteria derived from the mandatory baseline (see "The standards library"). **Prototype-assisted approval** (optional; offered when the work has a user-facing surface): the approval conversation may run against a running throwaway prototype (`timone-prototype`, [ADR-0011](doc/adr/0011-prototype-convention.md)) — the human reacts to a preview URL while the agent maps what they see to requirement IDs and folds reactions into the list. The gate itself is unchanged: approval lands on the requirement list, never on the prototype, and every divergence between prototype and list is surfaced explicitly before approval is requested — a prototype under-specifies by nature (error paths, priorities, non-UI and accessibility criteria).

**4 — Architecture.** ADRs record decisions passing the three-part significance test — **hard to reverse**, **surprising without context**, and **the result of a real trade-off**; if any part is missing, no ADR. They are standalone artifacts created the moment the decision is made — in a grill session, during planning, or mid-execution — **never scheduled as plan work**. Format: Status / Date / Context / Decision / Consequences. Superseding creates a new ADR and flips the old one's status with a cross-link; history is never edited. Reference examples: Timone's own `doc/adr/0001`–`0006`.

**5 — Planning.** A phase is a coherent, end-to-end-testable increment cut into thin vertical slices (schema → API → UI, not layer-by-layer), each sub-phase independently executable by a fresh-context sub-agent with copy-pasteable validation commands. Docs last; seed data second-to-last. Requirements map at phase level, never per sub-phase. Each sub-phase declares its **seams under test** — the public boundaries its tests will observe behaviour at — agreed at planning time; implementation writes tests only at declared seams. Prefactoring comes first when it makes the change easy ("make the change easy, then make the easy change"). Wide mechanical refactors (blast radius across the codebase) are the sanctioned exception to vertical slicing: sequence them as **expand–contract** (add the new form beside the old → migrate call sites in batches → delete the old form). **Required elements:** a phase file carries the requirement IDs it delivers (per the phase-level mapping rule above) and, per sub-phase, file markers naming every file created or modified, an explicit dependency statement, the declared seams under test, and copy-pasteable validation commands with the assertions they must satisfy. Sub-phases carrying no code say so rather than omitting the seams silently. The document layout that carries these elements belongs to the plan skill, not to this spec. **PRD anchoring:** feature phases list the requirement IDs they deliver; technical/enabler phases may be explicitly stamped un-anchored with human agreement. **ADR gate:** if planned work implies a significant undocumented decision, stop and record the ADR before the plan is written. **Status lifecycle:** the phase file carries a `Status` line from birth, and it is the written trace of this stage's gate — `Approved for execution by <who> <date>` when the plan skill writes it, since approval precedes the write; `Awaiting approval` for a plan file that exists without approval (hand-authored, or amended in a way that needs re-approval); `Complete — see <report>` at phase close. **Amendments:** an approved plan is amended in place, never silently rewritten — every change made after approval carries a dated `✏ Refined <date>:` marker so execution can see what moved, and sub-phases added mid-phase take the next free letter with the same marker. **Re-approval:** an amendment that *reduces* scope — striking an assertion, correcting a defect execution found, tightening wording — keeps the existing approval stamp, since the human already approved more than what remains; an amendment that *changes or grows* scope — a new sub-phase, a new file marker, a changed seam, a new assertion — voids the stamp, reverting the file to `Awaiting approval` until a human re-approves. Scope growing beyond an amendment is a new phase, not a bigger one; post-delivery plan changes are stage 9's "plan patch".

**6 — Implementation.** The orchestrator decomposes the phase into per-sub-phase sub-agent runs — fresh context each, only the relevant plan excerpt, prior handoff, and file list. Sequential by default; parallel only for slices sharing zero files. Within a sub-phase the loop is **TDD, red before green**: write a failing test at a declared seam, run it red, implement just enough to go green, repeat — one slice at a time, no speculative features. Anti-patterns are rejected: implementation-coupled tests (break on refactor without behaviour change), tautological assertions (expected value recomputed the code's way), and horizontal slicing (all tests first — bulk tests verify imagined behaviour). Refactoring is deferred to the delivery review **for identification**, not to the red→green loop — stage 8 raises it and stage 9 remediates it; delivery itself never commits code, since a refactor landing after the verification report would invalidate that report's evidence at the moment it is presented. Type-check regularly, run single test files during the loop, the full suite once at the end. A sub-phase is complete only when its validation checklist passes. Bounded retries (max 2 per sub-phase), then escalate to the human. **Entry gate:** a phase file not stamped `Approved for execution` is not executable — execution refuses, routing to the human when the plan was never approved (re-planning cannot manufacture a missing approval) and to stage 5 when an amendment is what left the stamp stale. **Work branch and commits:** one branch per phase, named `phase-NN-<slug>`, cut from the project's default branch — or, when the previous phase is complete but still **unmerged**, stacked on that phase's branch instead and said so in the completion report, since merging is stage 8's and a human's, so a completed phase awaiting review is the normal state and a rule demanding the default branch would mean no project could ever start its second phase; execution refuses to start on a dirty working tree, or on an existing branch of that name carrying divergent commits. **Dirty** means tracked modifications or untracked files that are not the phase's own artifacts: the phase file, the handoff file, the completion report and the ordinary products of a dependency install are never the dirt that blocks a start, since the escalation path deliberately leaves in-flight work behind and an escalated phase must remain resumable. One commit per sub-phase, made only **after** that sub-phase's validation passes, messaged `<type>: NNx — <deliverable>` — so `git log` alone answers which slices actually landed. The phase-close write (completion report plus the `Status` flip) is not a sub-phase and carries no `NNx`: `docs: close phase NN — <theme>`, mirroring stage 5's `docs: plan phase NN — <theme>`. **Handoff notes** carry what the slice built, the files it touched, decisions taken inside the slice, its validation evidence including the red-green trace, and anything the next slice must know; they are appended to `doc/plans/phases/reports/phase-NN-handoffs.md`, one section per sub-phase, committed with that sub-phase's commit. **Completion report** (`doc/plans/phases/reports/phase-NN-complete.md`) **required elements:** the date, a link to the plan with its approval trace, the requirement IDs delivered and their resulting statuses, a per-sub-phase outcome table carrying commit SHAs, deviations from the plan, and context for the next agent. **Escalation, concretely:** after two failed attempts at a sub-phase's validation, execution stops, starts no dependent sub-phase, and reports the failing validation step with both attempts; because commits happen only after validation passes, the branch is left at the last passing sub-phase and the failing work stays uncommitted in the working tree — the escalation says so rather than leaving the state to inference. As in stage 5, the document layout carrying these elements belongs to the execute skill, not to this spec.

**7 — Verification.** A verifier context that did **not** watch the build checks observable behaviour against the criteria register — trusting only the running app, never source-code intent. Channels: `api` (terminal-checkable, forms the standing regression suite), `browser`, `human` (both reported as HUMAN-CHECK with a precise manual script). **Verdicts:** PASS / FAIL / HUMAN-CHECK / BLOCKED. REGRESSION is the FAIL variant reserved for a criterion that entered the pass already `verified` — the same failure class (it counts against the gate's zero-regressions clause and consumes the same fix loop), a distinct label because it means shipped behaviour broke and stage 9 reads it differently. BLOCKED means the check could not run at all — environment down, tooling absent, criterion unverifiable as written; it asserts nothing about behaviour, leaves the register untouched, blocks the gate, routes to the human, and consumes no fix loop. **Independence:** the verifier reads from a closed list — the criteria register(s), the PRD narrative, the phase file's `Status` and requirements header (never sub-phase bodies), the completion report whole, a prior verification report's HUMAN-CHECK-scripts section alone (and only that section — the obligation to re-issue a carried-forward script verbatim cannot otherwise be discharged from the list, and a stage-7 artifact carries evidence, never build knowledge), the project's `README.md`, `CONTEXT.md`, `doc/standards.md` and `STATUS.md` (which stage 7 is obliged to update), the operational configuration standing the app up rather than implementing it — compose files, `.env`/`.env.example`, the run and test scripts a package manifest declares — and Timone's standards baseline — and the report declares what was read. Expected behaviour comes only from the register; the completion report supplies operational facts (how to run the app, carried-forward HUMAN-CHECKs), never expected values. Never read: handoff notes, diffs or `git show` of code, anything under the source tree including the committed test suite, and ADRs. The project's own suite may run once as a build-health smoke, reported as such, but is never criterion evidence — evidence comes from verifier-authored throwaway probes, in scratch space, never committed. **Scope:** a pass covers the requirement IDs the phase claims plus the standing regression set — every criterion with priority MUST, verify-via `api` and status `verified`, computed from the register at verify time (derived, never maintained as a second artifact); each report lists the derived set so the computation audits. For an un-anchored phase the claimed set is empty by design: the pass is the regression set plus carried-forward HUMAN-CHECK items from the completion report, and the gate degenerates to zero regressions — stage 6's validation already covered the un-anchored deliverable itself. **Environment:** verification observes the deliverable in its production form where the stack distinguishes one — a production build, never the dev server. Browser-channel checks for user-facing deliverables include the baseline accessibility checks (automated scan where tooling exists, HUMAN-CHECK script otherwise); scan violations are failures. **Fix loops:** the verifier never fixes — fixing means reading source, and a verifier that has read the fix has build knowledge for the re-verify. Each FAIL produces a defect brief — criterion ID, expected per the register, observed behaviour, reproduction commands, evidence — and a fresh fix context implements and commits `fix: verify NN — <criterion-id> <slug>` on the phase's branch; the verifier ingests only the returned commit SHA, never the fix transcript. One loop is all of a pass's FAILs briefed and fixed followed by one full re-verify of everything except already-scripted HUMAN-CHECKs. Max 2 loops after the initial pass, then remaining failures are recorded with evidence, the register flips to `failed`, and the work goes to the human via stage 9. **Register writes:** only this stage writes the register's **verdict** statuses — `draft` / `verified` / `failed`, the evidence-driven ones — once per pass, at pass conclusion, in the same commit as the report, `docs: verify phase NN — <theme>` on the phase's branch; the report-flip coupling in one commit is the evidence link, and the register line itself stays bare. The register's **intent** transitions (`revised`, `DEPRECATED`) are the one carve-out: they are stage 9's, made in the same commit as the PRD amendment that motivates them, and they assert nothing about behaviour — a `revised` criterion returns here for a fresh verdict. **A `revised` line re-enters exactly as a `draft` one does** — stage 9 sets it when intent moves, and the next pass writes a fresh verdict on the new wording: a criterion whose text changed has no evidence until it is re-checked, and a requirement gaining a clause loses `verified` as a whole, since a requirement's status is the weakest of its clauses' outcomes. `draft` or `revised` → `verified` on PASS; `draft` or `revised` → `failed` at loop exhaustion; `verified` → `failed` on an unresolved REGRESSION, with a dated ✏ marker naming the report; a requirement carrying an unperformed HUMAN-CHECK clause stays `draft` with a dated partial-evidence marker linking the report and the script — a requirement's status is the weakest of its clauses' outcomes. **Verification report required elements:** the date and scope statement (or the un-anchored stamp), a verdict summary table (ID / priority / channel / verdict / loop), the environment and an independence declaration naming what was read, per-criterion evidence with commands as run and per-clause outcomes, HUMAN-CHECK scripts verbatim, a regression section stated even when empty, fix-loop accounting, register changes, and a handed-to-the-human section whenever anything remains. Re-verifying an already-reported phase appends an iteration section to the existing report, never a second file. As in stages 5 and 6, the document layout carrying these elements belongs to the verify skill, not to this spec.

**8 — Delivery.** Delivery presents finished work for human judgement; it does not improve it, does not merge it, and decides nothing the pull request exists to let a human decide. **Entry gate:** a phase stamped `Complete — see <report>` whose verification report exists and whose stage-7 gate passed — every MUST criterion PASS or HUMAN-CHECK, zero unresolved regressions, within 2 fix loops. A phase `Complete` with no verification report refuses and routes to stage 7; any register status of `failed`, or any BLOCKED verdict, refuses and routes to stage 9, since a failed pass has already spent its loops. **An unperformed HUMAN-CHECK does not block delivery** — it is carried into the PR body as an explicit, unticked checklist item naming where its script lives, because merging is a human act and the PR is where that human already is; its requirement stays `draft`, and delivery never writes the criteria register. **Gate order is input resolution → phase `Complete` → verification gate → platform binding:** gates about the work precede gates about where it goes, so an unverified phase hears that rather than a complaint about its host.

Before the PR opens, a **two-axis review** runs as parallel fresh-context sub-agents, each with its own read list. **Standards** reads the phase's diff, the project's `doc/standards.md`, the code-smell review reference, and the project's tool configuration — the last so it can *skip* what linting, formatting and type-checking already enforce; repo standards override the smell reference on conflict. **Spec** reads the diff, the PRD pair, and the phase file's requirements header, and asks whether the diff faithfully implements the PRD, flagging missing requirements, scope creep, and wrong-looking implementations. Neither axis reads the other's report, and **neither reads the verification report** — behaviour evidence is stage 7's, and a spec reviewer holding a PASS table reviews the report instead of the diff. The axes are reported separately, never merged into one ranked list: standards-clean code can build the wrong thing, and spec-faithful code can break conventions. **The reviews report; they never block, and they never refactor.** Findings do not withhold the PR — a review that withheld it would hide its own findings from the only person who can act on them. Refactoring identified at the delivery review is raised in the Standards report and executed through stage 9: code committed after the verification report and before the human's read would invalidate stage 7's evidence at the moment it is being presented.

**Both reports are committed artifacts**, not PR prose alone (ADR-0006 — the repo is the source of truth; a PR body lives on a platform): `doc/plans/phases/reports/phase-NN-delivery.md` carries both axes verbatim, the PR URL, and the scope and verification summary the PR body quotes, committed on the phase's branch as `docs: deliver phase NN — <theme>` **before** the PR opens. Work then lands as a pull request. **Required elements:** a title following the phase's convention; the driving ticket reference, or the requirement IDs when the project has no ticket home; a scope summary; the verification outcome as a verdict table, with outstanding HUMAN-CHECKs as unticked checklist items; both review reports under distinct headings, Spec findings quoting requirement IDs; a link to the committed delivery report; and the base branch with its reason whenever it is not the default branch. **Stacked branches:** when the phase's branch was cut from a previous phase's unmerged branch (stage 6's stacking rule), the PR is opened against *that parent branch*, not the default branch, and the body says which PR must merge first — delivery never merges and never rebases, so merge order is the human's. **Platform binding:** per ADR-0004 the PR *is* this stage's artifact, so a project whose `repo_url` is not GitHub-hosted is refused loudly and routed to the human — unlike stage 1's triage record there is no doc-record fallback, because a delivery record without a review surface would mean shipping nothing while reporting success; `gh` absent or unauthenticated refuses the same way. **Re-delivery updates, never forks:** a branch that already has an open PR gets that PR's body refreshed and an iteration section appended to the existing delivery report — never a second PR, never a second file. Merging is a human act (or an explicitly configured auto-merge policy, later). As in stages 5 to 7, the document layout carrying these elements — the PR body, the delivery report, the shape shared by both review sections — belongs to the deliver skill, not to this spec.

**9 — Feedback.** Feedback is the process listening. Stage 9 diagnoses what a reaction to delivered work *means*, proposes a response, and — once the human has confirmed it — routes that response to the stages that already exist. The classification is the diagnosis; the pipeline is the treatment. **Managed projects only:** feedback on Timone itself stays hand-run, as Timone's own planning already is.

**Intake.** Feedback on work the process has already produced or already promised, on a managed project, arriving as: a stage-1 triage record routed here (bug / post-delivery observation); delivery-review findings the human names for action; a stage-7 loop-exhaustion or BLOCKED hand-off, or a register line at `failed`; the outcome of a performed HUMAN-CHECK; or free-form human reaction to delivered work. **A stage-1 record may predate the work it reports on** — triage classifies a request against the PRD, not against a running app, so a bug routed here before the feature was built is normal intake, and it closes as *already resolved* once the build caught up. **Input resolution never hunts:** the invocation names the project and the feedback source — a record path, a PR or finding reference, or the feedback text itself — and reading that named source in full, plus the artifacts it cites, *is* the resolution; trawling the project for unnamed grievances is not. Stage 9 never manufactures feedback.

**Surfaced, not tabled.** Reading the artifacts a source cites will sometimes expose a defect nobody raised. **The item set of an intake is exactly what its named source raises** — that is what makes the no-hunting rule auditable, rather than a rule about the agent's private motive. What was noticed elsewhere is *recorded in the feedback record* as a candidate intake the human may name later, never triaged, never proposed, never acted on. Silence about it would be the shrug the three-answer layer question exists to prevent; tabling it would be manufacturing feedback. **Bound it:** one line each, and nothing already recorded as open somewhere the human reads — when it is tracked elsewhere, say where instead of restating it.

**Raised, not named** is a third thing, and it is neither of the above. When the invocation names one finding inside a document that carries several, the others were raised — by the source document, not by the agent — but they are not this intake's items. They are listed in the record by reference alone, as intakes the human may name; the alternative is either swallowing live findings or triaging what nobody asked for.

**The feedback record is this stage's artifact** — `doc/feedback/NNN-<slug>.md` in the target project, NNN zero-padded and allocated by scanning existing records exactly as stage 1's triage records are, one record per intake (an intake may bundle many findings from one source). It carries the source, the per-item triage table (layer / classification / proposed remediation / the human's decision), the amendments made, and the dispatch trace. When the source is a GitHub PR or issue, a comment links the committed record (ADR-0004); the record itself is always the committed file (ADR-0006), never PR prose alone.

**Layer triage comes first, and it admits three answers:** does this change **what we want** (intent), **how it was built** (implementation), or **neither — the record is wrong** (the artifacts misdescribe what exists)? The third answer earns its place because feedback like a stale non-conformance line in a delivery report is neither a requirements change nor a code change, and a two-way question trains agents to shrug one way silently. A batch is layered item by item, never wholesale.

**Intent moves the PRD before any code moves** (ADR-0006 — the pair is the source of truth for intent): same ID forever, criteria updated in place, `Status: revised` — or `DEPRECATED` with a one-line reason, the block staying — and a dated ✏ marker naming the feedback record. **Register carve-out:** verdict transitions (`draft` / `verified` / `failed`) remain stage 7's exclusive writes; intent transitions (`revised`, `DEPRECATED`) are stage 9's, made in the same commit as the PRD amendment they belong to. A `revised` criterion leaves the derived regression set until stage 7 re-verifies it against its new wording — its old evidence is stale by construction, which is what marking it means, **so an intent amendment always dispatches a verification pass**, even when it moves no code: a MUST left `revised` with nothing queued to re-verify it has quietly stopped being regression-checked. The register's *evidence* notes — the dated partial-evidence markers recording what a pass actually checked — are stage 7's too, and stage 9 routes a stale one there rather than correcting it.

**Classification is one of seven, each with a defined vehicle.** **Bug fix** — behaviour diverges from an unchanged requirement; a REGRESSION arriving from stage 7 defaults here. **Refinement** — the requirement is met and the quality is improvable; the delivery Standards axis's native output, riding as un-anchored work protected by the regression set. **Plan patch** — an existing plan file is wrong; stage 5's amendment rules apply, re-approval semantics included. **New sub-phase** — scope grows within a phase whose branch is still open. **New phase** — scope grows beyond one phase. **Record correction** — a committed **process artifact** misdescribes reality: a completion, verification or delivery report, `doc/standards.md`, a plan file's statement of fact, an earlier triage or feedback record; a docs-only correction stage 9 makes itself, naming the evidence for it. **Verification pass** — the artifacts cannot settle the item and only observed behaviour can: an unperformed HUMAN-CHECK whose requirement is still `draft`, a criterion left `revised` by an intent amendment, or a register evidence note that overstates what was actually checked; dispatched to **stage 7**, which owns every verdict and every claim about behaviour. Classification decides nothing about priority: priority is the human's, at the gate.

**Two boundaries the record layer needs, because the misdescribing artifact is not always stage 9's to fix.** When it is **application code**, the layer is still *record*, but the vehicle is a dispatched **refinement**: stage 9 never commits code, and that rule does not bend for a one-line comment. When it is a **register evidence note**, the correction is **stage 7's**, for the same reason its verdicts are — a claim about what was checked is a claim about behaviour. Without these two boundaries the layer table appears to force a docs-only vehicle onto artifacts stage 9 may not touch.

**The boundary is location, not judgement.** A **committed process artifact** — stage 9's to correct — is everything under `doc/`, plus `CONTEXT.md` and `STATUS.md`. Everything else the repository holds — source, schema files, tooling config, the `README.md` — dispatches as a refinement, however trivial the wording change. Drawing the line by file path rather than by what a file "really is" keeps a schema comment and a standards entry from being argued into the same class.

**"None" is a classification.** An item needing no remediation carries it explicitly, with its degenerate outcome; it is not an empty cell. **An intent-layer item carries two things:** the PRD amendment, which the *layer* implies and stage 9 makes, and the follow-on class for whatever work the amendment then requires — plus the verification pass that every intent amendment dispatches.

**The confirmation gate is stage 9's own.** Stage 9 proposes — per item: layer, classification, vehicle, scope — and stops. The human decides per item: **confirm, decline, or defer**; declined and deferred items are recorded in the feedback record with the human's reason, never argued with and never silently dropped. Only confirmed items move, and nothing moves before the gate. **For an item proposed with no remediation, confirm confirms the close** — the three words answer the *proposal*, not a vehicle, so an item classed "none" is confirmable exactly like any other; declining one means the human rejects the diagnosis, and the item stays open with their reason recorded. This gate answers *"is this the right response to the feedback?"*; stage 5's approval still answers *"is this breakdown executable?"* for whatever plan work the confirmation dispatches — collapsing the two would let a feedback conversation silently approve a plan nobody has read.

**Stage 9 routes; it never implements.** It commits **documents only**: the feedback record, PRD-pair amendments, record corrections to committed process artifacts, and `STATUS.md`. Every code remediation is dispatched — plan-file vehicles to stage 5, then through stages 6 → 7 → 8 like any other work. Code committed by stage 9 would be code no verification pass has seen and no delivery review has read: the exact hole stage 8 closes by refusing to refactor, reopened one stage later. The ceremony costs a sub-phase in a plan file; the invariant it buys is that nothing lands unverified and unreviewed.

**The vehicle follows the branch state.** Feedback on a phase whose PR is **open**: the remediation lands on that phase — plan amendment per stage 5's rules, execution on the same branch, stage 7 re-verifies, stage 8 re-delivers as an iteration of the existing PR. Feedback on **merged** work: a new phase file, a new branch, a new PR — merged work is history, and history is never rewritten. Record corrections follow the artifact they correct: one living on an open branch is corrected there (and a process-artifact-only change does not re-run the delivery axes, per stage 8's subject rule); one whose work is merged is corrected on the default branch, or on the next relevant branch when one is open.

**Degenerate outcomes are outcomes.** *Already resolved* (the divergence no longer exists — built away and verified since, or never built as reported because the report predated the build and what was built conforms), *not reproducible*, *working as intended* (the requirement says what the reporter wishes it didn't), and *declined by the human* all close the intake with the evidence cited — the register's and the reports' existing evidence, never a fresh behaviour probe, because behaviour evidence is stage 7's. An intake closed with remediation "none" is a completed stage-9 pass, not a failure of one.

**What stage 9 never does:** never merges, never verifies behaviour, never commits application code, never writes verdict transitions, never manufactures feedback, never overrides a decline. As in stages 5 to 8, the document layout carrying these elements — the feedback record and the proposal presented at the gate — belongs to the improve skill, not to this spec.

**10 — Deployment / 11 — Maintenance.** Stages defined so the process is complete end-to-end; their skills are post-MVP (see PRD-01 out-of-scope). Deployment releases a merged state to a target environment via the project's platform bindings. Maintenance turns dependency updates and production issues into triaged intake for stage 1.

## The standards library

Timone hosts the central standards library under `standards/` in its own repo, in three tiers:

- **Baseline (mandatory, all projects, no opt-out):** UI/UX guidelines and **accessibility** — a legal requirement under the European Accessibility Act (Directive (EU) 2019/882, applicable since 2025-06-28); working baseline EN 301 549 / WCAG 2.1 AA. Every project's `doc/standards.md` includes the baseline unconditionally. Enforcement points: user-facing PRD requirements carry accessibility acceptance criteria (stage 3), browser-channel verification includes accessibility checks (stage 7), and the delivery Standards review covers the baseline (stage 8).
- **Stack entries (selected per project):** TypeScript, Next.js, Prisma/PostgreSQL, better-auth, testing, Docker Compose local, Vercel + Supabase live, …
- **Review references (applied by stage 8 to every project, overridable):** the code-smell reference the delivery Standards review checks a diff against. A project's own `doc/standards.md` overrides it on conflict — which is why this is not the mandatory baseline, a tier that admits no exceptions. This tier is also the sanctioned exception to the "true of every project on Earth" rule below: a review checklist shared across projects is universal by construction, and a per-project smell list would make two reviews incomparable.

Content is authored and reviewed by the human, versioned centrally, injected into sessions like the stage skills. Discipline: tool-enforceable rules live in tool config (the eslint/tsconfig/prettier setup *is* the standard); library entries capture only what tooling cannot enforce; a line that would be true of every project on Earth doesn't belong. Each project's `doc/standards.md` = baseline + selected entries + recorded deviations — central evolution, project-level exceptions (the baseline admits none).

## Cross-cutting utilities

Not lifecycle stages of a feature — these apply across sessions and phases rather than within one pass through stages 0–11.

**Status reporting.** No owning skill — an obligation on **every** stage. Whenever a stage completes work, it updates `STATUS.md` (at the managed project's root, or Timone's root for Timone's own phases) so the human can see where things stand without reading a phase file. Plain language, no unglossed process jargon, and it always says **which** repository an item belongs to — the commonest confusion is not knowing whether the next action sits on a managed project or on Timone itself. It states what is done, what is in progress, what happens next, and what is waiting on the human. It is written **for** the human and is never an agent's source of truth: the PRD, phase files and reports remain the authorities, and `STATUS.md` must be regenerable from them without loss. A stage that changes a project's state and leaves this file stale has not finished. Requirement: [PRD-01.R22](doc/specs/prd/prd-01-process-layer.criteria.md).

**It is written only on the project's default branch — never on a work branch.** Every stage rewrites the whole file, and unlike the phase-scoped reports (one file per phase, so two phases never touch the same one) there is only ever one `STATUS.md`. Two work branches that both update it conflict the moment the second one merges, and a merge conflict in the artifact whose entire purpose is to tell the human where things stand is the worst possible place to have one. It is also where the human reads: the default branch is the one they open. **Mechanics:** the stage commits it on the default branch as its own commit — `docs: STATUS.md — <theme>` — **pushes that commit to `origin`**, and then **returns the clone to the branch it was on**; a stage that leaves the clone somewhere other than it found it has not finished. **Accepted consequence:** the file therefore describes work that is not yet merged, so every item names which branch and which pull request it belongs to. That naming is not optional — it is what makes a default-branch file able to describe in-flight work at all.

**Every stage pushes what it commits, and the push is part of the obligation, not a courtesy afterwards.** This applies to the whole of a stage's output — the artifacts on a work branch as much as `STATUS.md` on the default branch. A commit that exists only in the local clone is invisible to the human this file is written for, invisible to any other machine, and lost with the working copy; "committed" and "delivered to the reader" are not the same claim, and the process must not let a stage report the second while having done only the first. Stage 8 pushes today only because `gh pr create` refuses to open a pull request for an unpushed branch — an accident of one tool, not a rule, and no other stage has that accident to protect it. **The failure mode this closes is silent and asymmetric:** it never breaks anything locally, so the stage that commits without pushing looks exactly like a stage that finished, and the gap surfaces only when someone else — or the same person on another machine — goes looking for work that was reported done. It has been observed twice: stage 9's first live intake committed four feedback records nobody could open (2026-08-02, corrected in the skill), and a verification and a delivery pass in the same session each died between their commit and their push, leaving a report on disk and nothing on the remote. **A stage that has committed and not pushed has not finished**, and a stage interrupted between the two has stopped at an incomplete boundary rather than a clean one.

**Handover.** Owning skill: `timone-handover`. Purpose: capture the full state of an in-progress body of work — what's done, what's in flight, key decisions since the last handover, and the exact next action — so a fresh session or a different agent can resume without re-deriving context from the conversation. Two scopes: **meta** (Timone itself — which phases/PRDs are done, what's queued; artifact: `doc/handover/<date>-<slug>.md` in Timone's own repo) and **project** (one managed project's ticket/feature in flight; artifact: `projects/<name>/doc/handover/<date>-<slug>.md`). A handover doc references artifacts by path — PRDs, ADRs, phase files, reports — it never restates their content. Superseded handovers are kept, not deleted (same discipline as ADRs): the newest file for a scope is the current one.

**Prototyping.** Owning skill: `timone-prototype`. A prototype is a cheap, throwaway artifact built to be **reacted to rather than read**, answering one stated question — used by stage 2 at scale (a `prototype` ticket raising the fidelity of one open decision) and stage 3 (prototype-assisted approval), one convention for both ([ADR-0011](doc/adr/0011-prototype-convention.md)). It lives on a `prototype/NN-<slug>` branch in the project repo so the Docker preview machinery (ADR-0005) can serve it clickable — the human must be able to click it; a screenshot is not a prototype. It is **never merged and never the base of a work branch** — delivery refuses it, execution may not start from it, nothing is cherry-picked out of it. Fidelity is the cheapest that answers the question (static mock with fake data up to stubbed real-stack code), sized to one session. What survives is the human's reaction, recorded where the question lives — the ticket, or the requirement list under approval; the branch is deleted when the effort it served closes. Prototypes are exempt from the accessibility baseline (they ship to nobody), and an approved inaccessible prototype waives nothing — the PRD's accessibility criteria stand.

## Stable requirement IDs

- Format `PRD-NN.R<k>`. IDs are stable forever: never renumbered, never reused, never deleted.
- Intent changed → same ID, criteria updated, `Status: revised`, dated marker.
- No longer applies → `DEPRECATED` with a one-line reason; the block stays.
- New need → next unused ID.
- Every MUST has at least one Given/When/Then criterion and a verification hint; a MUST that can't be written testably gets sharpened with the human or downgraded.

## Gates and the human

Every stage's closing gate is either mechanical (validations pass) or human (a decision or review). Human gates are surfaced wherever the human is: interactively today; as ticket/PR comments once the inverted loop (PRD-02) drives these same stages. The daemon orchestrates stage skills — it never reimplements them.
