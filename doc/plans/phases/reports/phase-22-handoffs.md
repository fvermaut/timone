## 22a — ADR-0028, ADR-0029, and the ledger identity

> Built across two contexts. The first built the identity change; the second applied fvermaut's settledness ruling of 2026-08-15, wrote ADR-0029, and swept the eight test files the plan's refinement granted. The two halves are one slice and one commit.

**Built.** The ledger stops identifying a run with a ticket. A run's id is now `<project>#<ticket>/<seq>`, where `seq` is the chunk's sequence number within its ticket, and the ledger can hold several chunks for one ticket. `register` is idempotent by the ticket's **live** chunk rather than by the ticket: while an unsettled chunk exists it hands that one back, and once the ticket's current chunk is settled it opens the next sequence number. Two read methods join `RunStore` — `liveRunForTicket(project, ticket)` (the one unsettled chunk, or undefined) and `runsForTicket(project, ticket)` (all of them, in sequence order). A ledger written before chunk numbers existed loads unchanged: an id with no `/` is normalised to `/1` with `seq: 1` on every load, idempotently, at `version: 1` with no migration and no rewrite. The human-facing vocabulary is untouched — `timone retry ivtrends#1`, `timone takeover ivtrends#1` and the retry call to action still name a ticket, never a sequence. ADR-0028 records the five decisions fvermaut's approval of phase 22 settled.

**Built, second half — the settledness ruling.** *Settled* is the ledger's new, narrower idea of an ended chunk, and it is what lets a ticket move on. **Only `done` settles a chunk** (and `cancelled` will, once 22b lands); **`failed` does not.** `liveRunForTicket` therefore returns a failed chunk, `register` hands a failed chunk back with `created: false`, and no chunk is opened beside a failure. `TERMINAL` is untouched — still `["done", "failed"]`, still what frees the project for the next queued ticket at `promoteHead` — because a dead session must not freeze a project behind it. The two predicates answer different questions about the same status and are commented as such at their definitions. ADR-0029 records the ruling.

**Decisions taken inside the slice.**

- **`cta.ts:119` builds the command string directly.** This was **an instruction I was given by the orchestrator, not a decision I made**: the plan says the retry call to action keeps speaking `<project>#<ticket>` and that `cta.ts:119` is not touched, while its checkbox forbids any two-argument `runId` caller. The ruling was to stop calling `runId()` there and hand-build the string, exactly as `terminal.ts:15` and `prompts.ts:165` already do. The rendered output is byte-identical — `cta.test.ts` asserts the literal strings `timone retry scratch-app#13` and `timone retry ivtrends#1` and both still pass. No other line of `cta.ts` changed.

- **The five call sites ask for the ticket's *most recent* chunk — `store.runsForTicket(p, t).at(-1)` — not `liveRunForTicket`.** This is the one place I departed from the plan's literal wording ("must ask *the live one*"), and it is the item the orchestrator most needs to look at.

  The reason is that `TERMINAL` includes `failed`, so a failed chunk is not live. `retry.ts:82` exists precisely to re-arm a **failed** run; `cta.ts` renders the *"Something went wrong… run the command"* call to action only for a **failed** run, which `poll.ts:877` feeds; and `takeover.ts:129` answers for `done` and `failed` in full sentences. Passing `liveRunForTicket` to those three would have made `timone retry` unable to find anything to retry, deleted the failure call to action from every ticket, and turned takeover's "this is finished" answers into "I've never heard of this ticket". That is my production code being wrong, so I did not ship it.

  The composition is safe and loses nothing: **the live chunk, when one exists, is always the last** — `register` only opens a new sequence number once nothing of the ticket is live, so at most one non-terminal chunk exists and it is always the highest `seq`. `runsForTicket(...).at(-1)` therefore *is* `liveRunForTicket(...)` whenever a chunk is live, and is the chunk the ticket last finished on otherwise. For every single-chunk ticket — which is every ticket in every existing ledger — it is byte-for-byte what `store.get(runId(p, t))` returned before. `poll.ts:813` (the introduction guard, "a ticket the ledger is already working") became `runsForTicket(...).length > 0`, which likewise preserves today's "has this ticket any run at all" exactly; using `liveRunForTicket` there would have started introducing Timone on tickets whose work had finished.

  I added no third read method for this: the two the plan granted compose to it at each site, and `runsForTicket`'s doc comment carries the explanation of why the last element is the one the human-facing surfaces mean.

- **`SETTLED` is a second predicate over run status, not a narrowing of `TERMINAL`.** `TERMINAL` was left exactly as it was, including `failed`, and `promoteHead`'s trigger still reads it — so a failed run still frees its project for the next queued ticket, which is the behaviour the ruling explicitly must not change. What changed is one line in `loadedLiveRunForTicket`. Carrying two predicates over one enum is the sort of thing `standards/code-smells.md` would normally flag as a duplicate; it is not, and the comment at `SETTLED`'s definition exists so the next reader does not "clean it up". If you only read one thing in `runs.ts`, read that comment.

- **`seq` is required in `runSchema`, not optional.** Every other field added since the ledger was written is `.optional()` for forward compatibility, and I deliberately broke that pattern here: `seq` is half of a run's identity, and an optional one would push `number | undefined` through every caller for a state that the load-time normalisation guarantees cannot occur. The forward-compatibility promise is kept by the normalisation instead — `version` stays `1`, no file is migrated, and a rollback simply reads ids it wrote itself. **This is what breaks the type-check in two ungranted test files** (see below).

- **The normalisation runs before the schema parse, inside `readState`**, over raw `unknown`, narrowed with `typeof`/`in` rather than `as` (`standards/typescript.md` bans `as` as a parsing tool). It has to precede the parse because a required `seq` makes a pre-chunk file fail validation outright. It returns the input object untouched when the id already carries a `/`, so it allocates nothing on the hot path — `refresh()` re-reads the file at the top of every public read and every mutation.

- **The fixture is real, not invented.** The plan's checkbox asked for "a real pre-chunk `state.json` fixture", so the four runs are copied unchanged from the daemon's live ledger rather than hand-written, and were chosen to cover the shapes that differ (branch/no branch, PR/no PR, `parked`/`done`/`failed`, two projects).

## 22b — A run can end, and nothing starts on a closed ticket

**Built.** A run can now end because somebody decided it should, rather than only by finishing or breaking. `cancelled` joins `RunStatus` as a second dead end — `TRANSITIONS.cancelled` is empty, and it is reachable from `queued`, `picked-up`, `active`, `parked` and — after fvermaut's ruling of 2026-08-15, applied on top of the slice; see *"A failed run can be cancelled"* below — **`failed`**, but **not** from `done`. `RunStore.cancel(id, reason)` makes the move, records the reason on a new `cancellation` field, and clears whatever the run was waiting for. `cancelled` is in **both** `TERMINAL` (so an abandoned run frees its project and the queue behind it is promoted) and `SETTLED` (so its ticket may take a fresh chunk) — the obligation 22a's note 4 landed on this slice, and the thing that makes the poll loop's behaviour below self-healing.

**Built — `timone cancel <project>#<ticket> [--reason <text>]`.** It ends the ticket's current chunk and says so; everything that cannot be cancelled is refused with a sentence about what the ticket *is* doing, in `timone retry`'s discipline. It takes the ledger lock (ADR-0023) exactly as `retry` does, because cancelling is a ledger mutation and the daemon may be mid-cycle over the same file.

**Built — the poll loop refuses to start a session on a ticket that stopped being ours.** Before the spawn, `pollProject` checks the occupying `picked-up` run's ticket against the marked-and-open listing it already holds; a run whose ticket has left that listing is cancelled with the reason *"its ticket is no longer open and marked for me"* and no session is started. `PollResult` gains `cancelled: string[]`.

**Decisions taken inside the slice.**

- **A new `cancellation` field, not a reuse of `failure`.** The two words are read by people, and the surfaces that read them are substitution-shaped: `timone status` prints a failure as *"stopped early"* beside the command that restarts it, and `timone takeover` reports one as something that went wrong. A cancellation is neither — nothing broke and nothing will be retried — so a reason stored under `failure` would be one edit away from being announced as a fault at every one of those surfaces. It is optional, so `version` stays `1` and every existing ledger loads unchanged. The cost is a second nearly-identical optional string on `Run`; the comment at its definition says why it is not the duplicate it looks like, in the same spirit as `SETTLED` beside `TERMINAL`.

- **`store.retry` refuses a cancelled run in a sentence, and `retry.ts` was not touched** (it is ungranted, and did not need to be). Its `switch` has no `cancelled` case, so a cancelled run falls through to `store.retry`, whose throw the surrounding `catch` logs verbatim. The generic guard would have printed *"Run scratch-app#4/1 is cancelled, not failed — only a failed run can be retried"*: a state-machine complaint, with the ledger's internal id in it, in front of somebody who just typed a command. The `cancelled` guard sits above it and says what happened and what would start the work again. The exact words a human sees are in the evidence below.

- ~~**`timone cancel` refuses a *failed* run rather than cancelling it**, pointing at `timone retry`.~~ **Overturned by fvermaut's ruling of 2026-08-15 and no longer true** — see *"A failed run can be cancelled"* below. As first built, the plan's transition list stopped at the four non-terminal statuses and this bullet took it literally, on the reasoning that a failure is the one state retry recovers and that a failed chunk keeps holding its ticket precisely so that road stays open (ADR-0029). That reasoning defends the *retry* road and says nothing about a person who has decided not to take it; the refusal it produced was the last place a human could not clear a run without editing the ledger.

- **The reason names the observation, not a closure.** `noLongerListedReason()` is *"its ticket is no longer open and marked for me"*. `Ticket` carries no open/closed field and `listMarkedTickets` is `--state open` **and** marked, so absence from that listing is genuinely all the loop can see — and it covers the ticket being closed *and* the mark being taken off. Asserting a closure that was never read would be the ledger claiming to know something it does not.

- **The `cancelled` CTA offers no command.** A cancelled chunk was abandoned, not broken, so it must not read like the failure branch above it; and the command it would offer, `timone retry`, refuses it outright. What it says instead is the truth about what happens next: the chunk is settled, so a ticket still open and marked simply takes a fresh one on the next cycle. The branch is not cosmetic — without it a cancelled run falls into the parked branch, `waitingOnYou` comes back `true`, and `timone status` closes by asking the reader to answer on a ticket nothing is waiting on.

- **`status` states cancellations in their own group rather than in the project line.** `describeProject` partitions by `RUNNING` / `parked` / `queued`, so a cancelled run reaches `describeRun` from nowhere and the project reads `idle` — which is correct, the run holds nothing. `describeRun`'s fall-through was therefore left alone rather than given a `cancelled` arm that nothing can reach. The visible consequence a human needs is a line saying what was stopped and why, and it goes where the failures already go.

**One existing `poll.test.ts` assertion was corrected, and it is the item to look at.** `holds its peace once the label lands, without ever having been given a run` (in the introduction describe) walks a ticket through *unmarked → marked → unmarked* and asserted its run was still `picked-up` after the third cycle. Under this slice that third cycle **cancels** the run, because an unmarked ticket is absent from the marked-and-open listing. The assertion was changed from `"picked-up"` to `"cancelled"` and a comment added naming 22b; nothing else in the test moved, and its actual subject — that the introduction is posted once and not repeated — still passes untouched, because a cancelled run is still a run and `introduceUnmarked` skips any ticket that has one.

**This is a deliberate behaviour change and the orchestrator should confirm it.** Taking the `timone` label off a ticket now abandons the run that was about to start on it. The plan's refinement asks for exactly this — *"a closed ticket is one absent from the marked-and-open set"*, and the reason it dictates says *"open and marked"* rather than *"closed"* — and the alternative reading (keep working a ticket the human has explicitly taken back) is worse. It bites only the `picked-up` occupier: an `active` or `parked` run is untouched by this check.

### A failed run can be cancelled — the 2026-08-15 ruling, applied after the slice was built

**The ruling.** *`timone cancel` must be able to end a run that has already failed.* As 22b was first built, `cancelled` was reachable from `queued`, `picked-up`, `active` and `parked` only, which made clearing a failed run a two-command dance: `timone retry` to get it out of `failed`, then `timone cancel`. The window between the two is one the daemon polls, so it could pick the re-armed run up and spend real money on a fixture somebody was trying to delete. That left phase 20's finding 9 (*"no command ends a run"*) half-closed, and the live ledger's two failed runs were exactly that residue.

**What changed.** `failed → cancelled` joins `TRANSITIONS`, and that is the whole of the mechanism.

- `src/daemon/runs.ts` — `failed: ["picked-up", "cancelled"]`, with the reasoning at the row. `cancel(id, reason)` has no source-status guard of its own — it goes through `transition` like every other move — so there was nothing to keep in agreement. `TERMINAL` and `SETTLED` are untouched and already say the right thing: a cancelled run frees its project *and* settles its chunk, whatever it was cancelled out of.
- `src/commands/cancel.ts` — the `case "failed":` refusal arm is deleted and `failed` joins the statuses that fall through to the cancellation. **Nothing of its wording was kept:** it existed only to send the reader to `timone retry`, which is now the wrong advice, and its one true clause (*"it isn't running"*) is not something the person needs told before an action that succeeds. The retry road is still there, unadvertised and unchanged.
- **`done` is deliberately unchanged** and keeps an empty exit list. Finished work is not abandoned, and a new ticket is how you reopen it.
- **Both exits from `failed` exist and neither breaks the other.** `retry` re-arms the chunk in place; `cancel` abandons it. Because a cancellation settles the chunk, the ticket then takes a *fresh* one — a failure cancelled is not a failure resurrectable.

**Files touched:** `src/daemon/runs.ts`, `src/commands/cancel.ts`, `src/daemon/runs.test.ts` (+2, one corrected), `src/commands/cancel.test.ts` (one corrected), and this report. Nothing else needed changing — a search for other places stating *which statuses can be cancelled* found only these two: `TRANSITIONS` and `cancel.ts`'s switch. `poll.ts`, `status.ts`, `cta.ts` and `takeover.ts` all read a run's status rather than deciding what may be cancelled.

**Two existing tests encoded the old refusal and were corrected, not deleted.**

1. `runs.test.ts` → *"refuses to cancel a failed run, which is the one `timone retry` recovers"*, now **"cancels a failed run, so work nobody will retry can be ended"**. It asserted the exact refusal the ruling overturns, so it had to be inverted: it now asserts the move happens and the reason is recorded.
2. `cancel.test.ts` → *"refuses a failed run and points at the command that recovers it"*, now **"ends a failed run rather than sending the human via `timone retry`"**. Same reason, at the command seam, plus a `not.toContain("timone retry")` so the deleted advice cannot creep back.
