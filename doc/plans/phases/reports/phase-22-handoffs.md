## 22a — ADR-0028, ADR-0029, and the ledger identity

> Built across two contexts. The first built the identity change; the second applied fvermaut's settledness ruling of 2026-08-15, wrote ADR-0029, and swept the eight test files the plan's refinement granted. The two halves are one slice and one commit.

**Built.** The ledger stops identifying a run with a ticket. A run's id is now `<project>#<ticket>/<seq>`, where `seq` is the chunk's sequence number within its ticket, and the ledger can hold several chunks for one ticket. `register` is idempotent by the ticket's **live** chunk rather than by the ticket: while an unsettled chunk exists it hands that one back, and once the ticket's current chunk is settled it opens the next sequence number. Two read methods join `RunStore` — `liveRunForTicket(project, ticket)` (the one unsettled chunk, or undefined) and `runsForTicket(project, ticket)` (all of them, in sequence order). A ledger written before chunk numbers existed loads unchanged: an id with no `/` is normalised to `/1` with `seq: 1` on every load, idempotently, at `version: 1` with no migration and no rewrite. The human-facing vocabulary is untouched — `timone retry ivtrends#1`, `timone takeover ivtrends#1` and the retry call to action still name a ticket, never a sequence. ADR-0028 records the five decisions fvermaut's approval of phase 22 settled.

**Built, second half — the settledness ruling.** *Settled* is the ledger's new, narrower idea of an ended chunk, and it is what lets a ticket move on. **Only `done` settles a chunk** (and `cancelled` will, once 22b lands); **`failed` does not.** `liveRunForTicket` therefore returns a failed chunk, `register` hands a failed chunk back with `created: false`, and no chunk is opened beside a failure. `TERMINAL` is untouched — still `["done", "failed"]`, still what frees the project for the next queued ticket at `promoteHead` — because a dead session must not freeze a project behind it. The two predicates answer different questions about the same status and are commented as such at their definitions. ADR-0029 records the ruling.

**Decisions taken inside the slice.**

- **`cta.ts:119` builds the command string directly.** This was **an instruction I was given by the orchestrator, not a decision I made**: the plan says the retry call to action keeps speaking `<project>#<ticket>` and that `cta.ts:119` is not touched, while its checkbox forbids any two-argument `runId` caller. The ruling was to stop calling `runId()` there and hand-build the string, exactly as `terminal.ts:15` and `prompts.ts:165` already do. The rendered output is byte-identical — `cta.test.ts` asserts the literal strings `timone retry scratch-app#13` and `timone retry ivtrends#1` and both still pass. No other line of `cta.ts` changed.

- **The five call sites ask for the ticket's *most recent* chunk — `store.runsForTicket(p, t).at(-1)` — not `liveRunForTicket`.** This is the one place I departed from the plan's literal wording ("must ask *the live one*"), and it is the item the orchestrator most needs to look at.

  The reason is that `TERMINAL` includes `failed`, so a failed chunk is not live. `retry.ts:82` exists precisely to re-arm a **failed** run; `cta.ts` renders the *"Something went wrong… run the command"* call to action only for a **failed** run, which `poll.ts:877` feeds; and `takeover.ts:129` answers for `done` and `failed` in full sentences. Passing `liveRunForTicket` to those three would have made `timone retry` unable to find anything to retry, deleted the failure call to action from every ticket, and turned takeover's "this is finished" answers into "I've never heard of this ticket". That is my production code being wrong, so I did not ship it.

  The composition is safe and loses nothing: **the live chunk, when one exists, is always the last** — `register` only opens a new sequence number once nothing of the ticket is live, so at most one non-terminal chunk exists and it is always the highest `seq`. `runsForTicket(...).at(-1)` therefore *is* `liveRunForTicket(...)` whenever a chunk is live, and is the chunk the ticket last finished on otherwise. For every single-chunk ticket — which is every ticket in every existing ledger — it is byte-for-byte what `store.get(runId(p, t))` returned before. `poll.ts:813` (the introduction guard, "a ticket the ledger is already working") became `runsForTicket(...).length > 0`, which likewise preserves today's "has this ticket any run at all" exactly; using `liveRunForTicket` there would have started introducing Timone on tickets whose work had finished.

  I added no third read method for this: the two the plan granted compose to it at each site, and `runsForTicket`'s doc comment carries the explanation of why the last element is the one the human-facing surfaces mean.

- **`SETTLED` is a second predicate over run status, not a narrowing of `TERMINAL`.** `TERMINAL` was left exactly as it was, including `failed`, and `promoteHead`'s trigger still reads it — so a failed run still frees its project for the next queued ticket, which is the behaviour the ruling explicitly must not change. What changed is one line in `loadedLiveRunForTicket`. Carrying two predicates over one enum is the sort of thing `standards/code-smells.md` would normally flag as a duplicate; it is not, and the comment at `SETTLED`'s definition exists so the next reader does not "clean it up". If you only read one thing in `runs.ts`, read that comment.

- **`seq` is required in `runSchema`, not optional.** Every other field added since the ledger was written is `.optional()` for forward compatibility, and I deliberately broke that pattern here: `seq` is half of a run's identity, and an optional one would push `number | undefined` through every caller for a state that the load-time normalisation guarantees cannot occur. The forward-compatibility promise is kept by the normalisation instead — `version` stays `1`, no file is migrated, and a rollback simply reads ids it wrote itself. **This is what breaks the type-check in two ungranted test files** (see below).

- **The normalisation runs before the schema parse, inside `readState`**, over raw `unknown`, narrowed with `typeof`/`in` rather than `as` (`standards/typescript.md` bans `as` as a parsing tool). It has to precede the parse because a required `seq` makes a pre-chunk file fail validation outright. It returns the input object untouched when the id already carries a `/`, so it allocates nothing on the hot path — `refresh()` re-reads the file at the top of every public read and every mutation.

- **The fixture is real, not invented.** The plan's checkbox asked for "a real pre-chunk `state.json` fixture", so the four runs are copied unchanged from the daemon's live ledger rather than hand-written, and were chosen to cover the shapes that differ (branch/no branch, PR/no PR, `parked`/`done`/`failed`, two projects).

**Two existing assertions were corrected under the ruling.** Both were written by the first context hours earlier, encode the behaviour fvermaut has since ruled against, and are wrong rather than merely inconvenient:

- **`gives the project to the next chunk once the previous one has failed`** asserted `store.register` opening `scratch-app#7/2` after a failure and that chunk taking the project. That is the exact behaviour ADR-0029 forbids. Replaced by **`leaves a failed chunk retryable however often the poll loop re-registers`**, which registers again after the failure and asserts `store.retry(...)` still returns a `picked-up` run and the ticket still has exactly one chunk. Same scenario, opposite — and now correct — expectation.
- **`refuses to re-arm an earlier chunk while a later one is running`** asserted `retry` throwing `/scratch-app#7\/2/`. Its scenario is now **unreachable through the public API**: nothing can open chunk *N+1* beside an unsettled chunk *N*, so a failed chunk can never have a later chunk running over it. It was not deleted — the guard it aimed at is still covered, on a *different ticket*, by `refuses when another run has since claimed the project` in `describe("retry")`. Replaced by **`opens the next chunk once a retried chunk finally succeeds`** (fail → retry → activate → complete → chunk 2 opens), which is the property the ruling actually creates: a failure delays succession rather than ending it.

**What 22b and 22c must know.**

1. ~~**The ungranted-file fix is mechanical and is yours.**~~ **Done inside 22a**, on the refinement's grant. All eight files are swept, `npm test` is 832/832 and `npm run type-check` is clean. Nothing is left for you here. If you add a run to a fixture, its id needs a `/<seq>` — the store will not accept one without, and a hand-written *pre-chunk* ledger (no `/`) is still legal input and normalises on load.

2. **A ledger read only ever gives you a chunk; the breakdown gives you the initiative.** `liveRunForTicket` answers "is a chunk building", `runsForTicket` answers "which chunks has this ticket had". Neither can answer "is there a next chunk" — per ADR-0028 D1 that answer lives in `doc/plans/breakdowns/ticket-NN.md` in the project checkout, and D4's between-chunks call to action needs it. Nothing in the ledger will ever tell you, by design.

3. **Read `runsForTicket(...).at(-1)` as "the ticket's current chunk".** It is the idiom the five call sites use and the reason is written on `runsForTicket`'s doc comment. If you need "is anything building right now", that is `liveRunForTicket`, and under ADR-0029 the two now differ **only** when the last chunk is `done` — a failed chunk is returned by both. That makes the five call sites strictly safer than when they were written: `retry`, `takeover` and the failure call to action all want the failed chunk, and `liveRunForTicket` would now hand it to them too.

4. ~~**There is a live hazard in `register`'s new semantics…**~~ **Ruled on and closed inside 22a.** fvermaut ruled on 2026-08-15 that a failed chunk keeps holding its ticket until it is retried or cancelled; **ADR-0029** records it, and `SETTLED` / `isSettled` implement it. The symptom described — a ticket accumulating a chunk a minute after a failure — cannot occur, and `timone retry` is unchanged. **22b, this lands one obligation on you: `cancelled` must be added to `SETTLED`, not just to `TERMINAL`.** ADR-0029 says why — cancellation is the *other* way a ticket gets past a chunk, and the only way past a failure nobody wants retried. A `cancelled` status that is terminal but unsettled would leave an abandoned chunk holding its ticket forever, and the phase's own note that `cancelled` is "self-healing — a reopened ticket takes a fresh chunk from `register`" depends on it. There is already a `runs.test.ts` case to extend: `a ticket whose only run is cancelled accepts a new run`, which 22b's seam list names.

5. **`seq` is not an attempt count.** `RunStore.retry` re-arms a run in place and leaves `seq` alone, deliberately: the same chunk being built again is the same chunk. If anything downstream wants to count attempts, that is a different field and a different decision.

6. **Deferred refactoring** (per the plan, not done here): the three `store.runsForTicket(p, t).at(-1)` call sites in `poll.ts` re-read the state file three times per ticket per cycle where the old code did too, but through a filter-and-sort rather than a `find` — worth a single per-ticket lookup if a cycle ever gets hot. `TERMINAL`'s doc comment has been reworded off "Statuses a run never leaves" onto what it actually governs; nothing is outstanding there.

7. **The daemon has not been restarted against this code, and must be before anything is observed.** Nothing in this slice was exercised live: the ledger identity, the normalisation and the settledness rule are proved by the suite only. `.timone/state.json` was read for the fixture and not written.
