# Phase 19 — Sub-agent handoffs

> One section per sub-phase, appended in execution order, each committed with its own sub-phase's commit. Format per `process.md` stage 6.

## 19a — one writer, and it says who holds it

**Built.** The run ledger now has an exclusive lock, and only the process holding it may write. A second `timone daemon` — the `--once` typed while the first is still inside a session, which is the shape that bought two agent sessions for one written answer — prints one plain sentence naming the holder (`timone daemon (pid 4213) is already working this ledger — it took it at …`) and exits non-zero, having started nothing. `timone takeover` and `timone retry` take the same lock for the same reason: both spawn sessions, and both were racing the daemon. A lock is given back on every ordinary exit, on the throwing path, and on `SIGINT`/`SIGTERM`.

A holder that crashed does not wedge its project, and a holder that is merely busy is not robbed: **a lock is broken when, and only when, the process it names is gone** ([ADR-0025](../../../adr/0025-a-lock-holders-proof-of-life-is-its-process.md)). The staleness window survives as a cheap first filter — a holder that touched its lock moments ago is not asked about at all — and stops being the authority. So a daemon two hours into a session, and a daemon on a laptop that was shut, are both refused however long they have been quiet, because their processes still exist; and a daemon killed at the terminal is reclaimed on the next start, which says whom it took the ledger from. **Nothing on any path through acquisition reads or writes `state.json`**: acquisition touches the lock file beside it and nothing else, so a refused process no longer mutates the ledger it was just refused. The unit surface is untouched: `pollOnce` takes no lock and needed no change, because the lock is on the process, not on the cycle.

**Decisions taken inside the slice.**

- **The reclaim path was rebuilt onto ADR-0025 after the original witness design was found unbuildable.** An earlier context built 19a as first planned — the reclaim gated on `RunStore.witness` (ADR-0020). The build is what exposed the flaw: `witness()` ends in `this.persist()`, so *consulting* the evidence writes the file the lock protects. Two faults followed, both reproduced at the real defaults: a refused process mutated the ledger, and repeated refusals accumulated a continuous watch that earned the right to break a **live** daemon's lock in three `--once` starts a minute apart. fvermaut ruled on 2026-08-13 and ADR-0025 records it. **The witness is not consulted, not stamped, and not required anywhere in `lock.ts` or in `daemon.ts`'s acquisition.** ADR-0020 is untouched for *runs* and still governs them through `poll.ts`. This paragraph exists because a handoff describing the superseded design would mislead 19b and stage 7 about what is in the tree.
- **Liveness is injected, and the whole judgement is the probe's.** `isHolderAlive?: (holder) => boolean` receives the entire holder record, not a pid, because identity is the pid *together with* what the lock recorded (ADR-0025) and a caller with a better identity oracle must be able to use it. It is injected because a test cannot portably manufacture a dead pid: any number it picks may be live on the runner's machine, and a case asserting against whatever the pid table happens to hold asserts nothing.
- **The default probe is `process.kill(pid, 0)`, and `EPERM` reads as alive.** Signal 0 sends nothing; it asks the OS whether the pid exists and whether this process may signal it. `EPERM` means *alive and somebody else's* — reading it as death would let an unprivileged rival break a root daemon's lock. The recorded `command` is a human-facing label (`timone daemon`), not an OS command line, so there is nothing in `ps` output it could honestly be compared against; **pid reuse inside the staleness window therefore stays a bounded residual risk**, exactly as ADR-0025 accepts, and the seam to refine it is the injection point.
- **The window is checked before the probe, never after.** It is a filter, not a second authority — two rules deciding one question drift apart. Asserted by counting probe calls rather than argued.
- **`takeover` and `retry` reclaim on the same evidence a daemon does.** The superseded design withheld reclaim from them because only a poll loop recorded a witness; under ADR-0025 the question is one anybody can ask the OS, and there is no reason to withhold the answer. `retry` above all: it is the route back from a session that died holding the ledger, so being refused by the corpse of the daemon that died holding it would be the phase-14 fault returning under a new name.
- **A `token` per hold**, so a process whose lock *was* reclaimed cannot delete the reclaimer's lock on its way out — that would have handed the ledger to a third writer silently.
- **Refusals return, the work's own errors throw.** Per `standards/typescript.md`: acquisition failure is a domain failure (`{ ok: false, error }`); anything the wrapped work throws is re-thrown *after* the lock is back.
- **Creation is an exclusive create (`wx`), rewrites go through temp+rename** like `RunStore.persist`, so two processes starting in the same instant cannot both decide the ledger is free, and no reader ever sees half a lock.
- **A lock file that cannot be read is refused, not overwritten** — "delete it if no timone process is running". Overwriting a file it cannot read would be a process deciding on no evidence that nobody is there. This branch has **no test**: it is outside the plan's declared seams, and I did not add tests the plan did not declare.

## 19b — the claim precedes the work

**Built.** A run is taken out of the pool a second process could resume it from **before** the session that will do the work exists. `RunStore.claim` writes `parked → active` with no session id — there is none yet — and the spawner takes it immediately before `runtime.start`, which is the call that awaits the session's first message and used to hold the ledger at `parked` for its whole duration. If the spawn throws, the same path puts the run back on the wait it came from, with its `waitingOn`, its kind and its cursor as they were, and re-throws to whoever asked for the session: **a claim never outlives the session it was taken for**, which is the stuck-run fault this could have reintroduced. The session id still lands the moment there is one, so a guardrail report is filed against its run and not as `interactive`.

And the guards that make the claim mean anything across processes now read the file. `occupyingRun`, `runningRun` and `parkedRuns` — the three `poll.ts` guards on at `:638,639,642` — refresh before answering, so a daemon that has itself written nothing still sees the claim another daemon wrote a moment ago. Two processes walking the same parked run through the same guard sequence now serialize: the first resumes it, the second finds it taken and does nothing. Nothing a human reads changed, and `pollOnce` is untouched and untaken.

**Files touched.**

- `src/daemon/runs.ts` — `claim(id)` added: `parked → active` without a session id, and deliberately **without** clearing the wait. `occupyingRun` / `runningRun` / `parkedRuns` call `refresh()` first; two private twins (`loadedOccupyingRun`, `loadedRunningRun`) serve every caller that is already inside a mutation. `activate`'s three wait-clearing lines became `stopWaiting`, shared with nothing else yet — it exists so `claim` and `activate` cannot drift on what "stops waiting" means.

Both `runtime.start` sites go through it — `runStage` and `recordApproval` — so the gate-approval path is fixed by the same code rather than left as the one place the fault survives. `waitOf(run)` builds the release's `ParkOptions` from the run's own record. The two `const active = store.activate(...)` bindings, never read, are gone with the calls they made.

**Decisions taken inside the slice.**

- **`RunStore.claim` is a new method rather than `activate` with a placeholder id.** The claim has no session id, because the runtime has not been asked for one. Passing a made-up string would have put a lie in the field `runForSession` matches on — a real session's guardrail report filed against the wrong run — which is a worse fault than the one being closed. The plan named only the accessors for `runs.ts`; this is the API the session.ts half needs, and it is where the lifecycle rule already lives.
- **The claim leaves the wait on the run; `activate` clears it as before.** The claim exists to hold the slot for a session that may still fail to start. A claim that erased `waitCursor` and `waitingOn` first would leave a process that *crashed* mid-spawn — not threw, crashed — with no record of what the run was waiting for, and the in-memory snapshot the release path uses does not survive a crash. `timone status` pays nothing for this: it reads `waitingOn` only for a `parked` run.
- **Only a parked run is claimed.** A `picked-up` run is already claimed — that status occupies the project's session slot and every guard excludes it — so the entry spawn never had this fault; ADR-0023 traces it to the resume path and names the `parked → active` transition specifically. Claiming a picked-up run would also need an `active → picked-up` release the lifecycle does not allow, so it would have made the failure path *worse*.
- **The refresh is on the public accessors only, with private twins for callers inside a mutation.** This is not an optimisation and it is the one thing in the slice that could have been silently catastrophic: `transition`, `claimBranch` and `promoteHead` hold a live reference into `this.state` between `mutable()` and `persist()`, so a refresh in that window replaces the object the reference points into and the mutation is written to a state nobody persists. Every mutation would have become a no-op, and the accessor tests would still have passed. The split is documented on `loadedOccupyingRun` for whoever next adds a caller.
- **The release re-parks and re-throws, rather than failing the run.** `resumeAnswered` and `pollProject` already catch a throwing spawn, report it on the cycle's error list and leave the run alone; failing the run here would have changed what the human sees, which this phase may not do.

## 19c — reading an answer consumes it

**Built.** A written answer starts one session, and one only. Deciding to resume on it is the same act as consuming it: the poll loop advances the run's wait cursor to the last comment the answer was read from, on disk, **before** the spawner is called — so a second reader, whether another daemon or this loop on its next cycle, finds nothing outstanding on the same thread. And the session that answer starts can no longer hand it back: when it posts nothing, `afterConversation` used to re-park at the newest *machine* comment, which is the invitation the human had already replied to, and the next cycle read their reply again. **One daemon, alone, bought two sessions for one answer** — ADR-0023's fourth fault, the one needing no concurrency. It now re-parks no earlier than the instant its own session began, which is never before the answer.

**The answer itself is untouched.** Nothing edits it, nothing deletes it, nothing quotes it back; it stays on the ticket, permanent and public, and only the machine's marker moves. That is asserted against a seam recorder that demonstrably *does* see the machine's own post, so "nothing was written" is an observation rather than an empty log.

And consuming is no longer a one-way door. `timone retry` on a run waiting on a conversation winds its marker back to before the last answer read from it and says so, which is the route out of the window ADR-0023 accepts — the one where an answer is read, the session dies, and the ticket looks answered with nothing working on it. A human who sees a stalled ticket runs the command they already know; they are never asked whether the answer was "consumed".

**Files touched.**

- `src/daemon/poll.ts` — `resolveWait` now returns a `Resumption` (`{ context, consumed? }`) rather than a bare `SpawnContext`: what the session should do, and what reading the wait consumed to decide it. `resumeAnswered` reparks with `{ ...waitOf(run), waitCursor: consumed }` inside the same `try` as the spawn, immediately before it. `writtenAnswer` returns the words **and** the instant of the newest comment they were read from.
- `src/daemon/poll.test.ts` — a `reading a written answer consumes it` describe: three cases, with their own thread fixture and a call-recording adapter double.
- `src/daemon/session.ts` — `afterConversation`'s re-park cursor is `laterOf(waitCursorFrom(ticket), cursor)`; `laterOf` added; `waitOf` exported (it is now the one description of "the wait this run already had", used by the release path, the consume and the rewind).
- `src/daemon/session.test.ts` — a `written answer starts one session and no more` describe: the single-process re-fire, driven through two real poll cycles.
- `src/commands/retry.ts` — the `parked` arm calls a new `rewind`, which winds a conversation park's cursor back and returns 0; every other wait keeps the refusal it had, word for word.
- `src/commands/retry.test.ts` — a `the way back from a consumed answer` describe: one case, end to end through the ledger.

**Decisions taken inside the slice.**

- **Only a written answer is consumed.** ADR-0023 names the written path specifically, and it is the only wait whose *trigger is the comment itself*: a gate's answer clears its wait by moving the run to another stage, and a conversation record is the machine's own writing. Consuming a gate reply would have been a second mechanism doing what the stage transition already does.
- **The cursor is the newest comment the answer was read from, not the oldest.** `writtenAnswer` reads generously — everything they wrote after the park, joined — so consuming has to cover all of it or the tail re-fires on the next cycle. The newest is also the smallest advance that does that, which is what keeps a comment written *later* still audible; that is a declared case, not an argument.
- **The consume sits inside the spawn's own `try`.** 19b's constraint puts it before `spawner.spawn`; putting it inside the same `try` also means the one thing that can throw there — `repark` refusing because another process claimed the run between the guard and here — is reported as a cycle error and the project's cycle carries on, rather than aborting `pollProject` before it promotes its queue. A process losing that race must not spawn, and now it does not.
- **`resolveWait` returns the consumed instant rather than the caller recomputing it.** The alternative is reading the thread twice and judging it twice, and two readers of one thread are free to disagree about which comment the answer was. It cost five mechanical return sites; 19d should know they are shaped that way on purpose.
- **`waitOf` is exported rather than copied.** Three call sites now say "the wait it already had, with one field different". Three copies of that shape would be three places to forget the next field a wait acquires — the duplicated *decision* `standards/code-smells.md` names. The cost is `commands/retry.ts` importing `daemon/session.ts`; `commands/daemon.ts` already does.
- **The rewind is one millisecond, and it is exact where it matters.** The marker sits *at* the answer's own instant and a comment is unread only when strictly later, so the smallest step the timestamp can express makes that comment readable again and nothing else. **Its bound:** an answer written as several comments inside one poll interval is rewound to its last one. The honest fix is a second instant on the run, and `src/daemon/runs.ts` is not this slice's to change — so it is reported here rather than smuggled in. A wider rewind (the run's creation, say) would re-read comments that were never part of the answer, which is worse than losing the earlier half of a two-comment answer on a recovery path.
- **`retry` rewinds a conversation park whether or not anything was consumed**, because it cannot tell, and it must not ask the human to. Rewinding an untouched park re-reads nothing — there is no comment after the invitation — so the no-answer case is a no-op that costs a cycle. Every other wait keeps its old refusal, including the `parked`-on-a-gate case an existing test pins.
- **`retry` on a *failed* run is unchanged, and cannot rewind.** `activate` clears all three wait fields, so a run whose session really started and then died has no cursor left to wind back; re-arming it at its stage is what it already did, and the conversation stage re-invites. Left alone: changing it would be changing the entry path, not the consume.

## 19d — one fetch per parked run per cycle

**Built.** A parked run's decision is taken from **one** read of one thread. Asking whether the wait has ended and asking what the run should resume with are two questions about the same thread, and until now each fetched it for itself: a conversation park cost two `getTicket` calls per cycle, a review park two `getPullRequestThread` calls, whether or not anything had been said. Both halves now read through a per-run reader that fetches at most once, so the decision is **atomic with respect to the thread it is taken from** — the conclusion check and the resumption can no longer see different threads, which is the shape of fault [ADR-0023](../../../adr/0023-one-answer-one-session.md) is closing — and it is reached in one round trip instead of two. The saving is not confined to the resuming run: a run that sits parked and quiet is also asked about once a cycle now rather than twice.

**Nothing a human reads changed, and nothing the loop decides changed.** The diff is fetches, not judgement: same resumption, same spawn context, same consume, same ledger writes, same comments, same errors. That is asserted rather than claimed — each of the two cases pins the decision *and* the count, and the decision half was run green against the two-fetch implementation before the collapse, so "byte-identical" is an observation about both implementations rather than a hope about one.

**Files touched.**

- `src/daemon/poll.ts` — new module-private `RunThreads` (`ticket()` / `pullRequest(pr)`) and `threadsOf(run, project, adapter)`, which memoises each thread's first fetch. `resumeAnswered` builds one reader per parked run, inside the loop, and hands it to all three readers of the thread. `concludeReview` takes it in place of fetching; `concludeLastConversation` takes it and loses its now-unused `project` parameter; `resolveWait` takes it **instead of** `project` and `adapter`, so no branch inside it can reach the tracker at all. All four of its fetch sites and both of the conclude functions' now read through it.
- `src/daemon/poll.test.ts` — a `pollOnce — one read of one thread per parked run` describe: two cases, each with its own counting adapter, one for the conversation path and one for the review path.

**Decisions taken inside the slice.**

- **A per-run reader, rather than passing a pre-fetched thread down as a parameter.** Handing `concludeLastConversation`'s thread on to `resolveWait` — the shape 19c's handoff names as acceptable — would have meant an optional "already read this" argument on a function that has five wait branches, three of which want a ticket and one a pull request. The reader says the same thing in the type: `resolveWait` no longer holds an adapter, so a future branch *cannot* silently add a third fetch. It is the difference between the double fetch being fixed and it being made unexpressible.
- **The reader's lifetime is one run's turn, not the cycle.** A cycle-wide cache would answer a later run from a thread fetched before an earlier run's session had posted to it — staleness bought with the same coin the fault was, and the exact thing 19b's handoff warns against caching. Constructed inside the loop body, after the guards, so it cannot outlive the run it was built for.
- **`resolveWait` lost `project` and `adapter` rather than gaining a parameter.** Both existed in its signature only to make fetches. Passing the reader in their place keeps the parameter list at two and removes the module's only other route to the tracker from the function that had four of them.
- **`concludeLastConversation` lost `project` too**, which the fetch was its only use of. `concludeReview` keeps it — it still posts the merged/closed comment and closes the ticket through it — and therefore grows to six parameters, which is a smell and is recorded below rather than fixed here.
- **The pull-request memo is keyed by number, not assumed.** A run has one pull request today, so a single unkeyed slot would work; keyed, a call for a different number gets a fetch rather than the wrong thread. Four lines, and it removes a silent-wrong-answer failure mode from a helper whose whole job is to answer twice.
- **The repark was not hoisted with the fetch**, per 19c's binding note. The consume stays exactly where 19c put it: inside the spawn's own `try`, immediately before `spawner.spawn`, reading `resumption.consumed` — which is still derived from the same single read of the thread that produced the spawn context. Nothing about the consume's position, its `try`, or its error handling changed.
- **No lock was taken in `poll.ts`.** `pollOnce` is untouched and untaken; the reader is a memo, not mutual exclusion.

## 19g — the consumed answer survives the session that read it

**Built.** An answer the daemon has read is never asked for twice. Reading it advances the run's cursor past it (19c) and the session that acts on it clears the wait a moment later — so a session killed in between used to leave the run `failed` with **nothing at all pointing at the answer**, and `timone retry` fell through to the entry path and re-posted the original invitation verbatim over the human's own words. The run now records the *instant of the answer it read* in a field the wait's clearing does not touch, and `retry` winds the marker back **whichever state the run died in**: a `failed` run is re-armed and put back on the same conversation just before that answer, a `parked` one is rewound as it was since 19c. The next cycle then **resumes** — one session, carrying their words — instead of asking again, and the invitation stays posted once across the whole sequence.

The marker is present only while an answer has been read and not acted on. It survives `activate` and `fail`, and is dropped the moment the run shows it got somewhere: a new wait, the next stage, or the run resolving. So a marker that exists always names an answer nobody has finished with, `retry` needs nothing from the human but the ticket's name, and a run that failed at some *later* stage carries none and is re-armed exactly as it always was. **Nothing a human reads changed** except that a message stops being sent: no ticket wording, no resolution shape, no change to either answer path. The answer itself is untouched — still on the ticket, word for word, asserted as such.

**Files touched.**

- `src/daemon/runs.ts` — `Run.consumedAnswerAt` added (optional; `version` stays `1`, so every existing state file loads unchanged). `ParkOptions.consumedAnswerAt` with it, written by `applyPark` — so the consume sets it and every ordinary park clears it. `complete` clears it; `setStage` clears it **only when the stage actually changes**; `activate`/`stopWaiting` deliberately do not. No lock, no new accessor, and the `loadedOccupyingRun`/`loadedRunningRun` arrangement 19b built is untouched.
- `src/daemon/runs.test.ts` — a `the answer a run has read and not acted on` describe: three cases over the field's whole life.
- `src/daemon/poll.ts` — the consume's single `repark` now carries `consumedAnswerAt: resumption.consumed` beside `waitCursor`. One write, from the one read 19d established; its position, its `try` and its error handling are exactly as 19c and 19d left them.

**Decisions taken inside the slice.**

- **The marker is written through `ParkOptions`, not by a new store method.** The consume is already a `repark`, so this keeps it one ledger write rather than two, and it gets the clearing for free in the honest place: a park is a run waiting on something *new*, which means whatever it was holding has been acted on. A dedicated `consumeAnswer(id, at)` would have read better at the call site and then needed the same clearing bolted onto `applyPark` anyway.
- **`waitOf` was not changed, and could not be** — it lives in `session.ts`, outside this slice's granted files. Two consequences, both benign and both deliberate: `retry`'s rewind spends the marker for free (`{ ...waitOf(run), waitCursor: … }` carries none), and the failed-spawn release path (19b's `store.park(run.id, waitOf(parked))`) clears it. The release leaves the run parked with its cursor still *at* the answer, so `retry`'s cursor fallback recovers it there — the answer is not lost, only recovered by the older route.
- **`setStage` clears the marker only on a real change, and that guard is load-bearing.** `session.ts:496` re-records the stage a resumed session is about to run *before* it starts — so clearing unconditionally would discard the answer that session was resumed on, and the live fault would survive the fix. Proved by mutation: dropping the `!==` makes the died-`active` case fail again with two invitations. The clause exists because without it a run that consumed an answer at `clarification`, settled it, advanced, and then failed at `planning` would be rewound by `retry` onto a conversation at `planning` and handed the old answer as feedback — a wrong rewind of the operator's main recovery tool.
- **A `failed` run is re-armed *and* re-parked, in that order.** `failed → parked` is not a legal transition and must not become one; `store.retry` (`failed → picked-up`) then `store.park` (`picked-up → parked`) is two writes through the lifecycle as it stands. Between them the run is `picked-up`, which is a state the ledger already understands.
- **`retry` supplies the re-park's `waitingOn` itself** — "the answer you wrote on the ticket, which I'll read again". `activate` cleared the original text and the marker carries only the instant, per the plan; hardcoding the channel's `"a conversation in your terminal"` would claim they are expected to talk when they have already written. It is what `timone status` shows for the one cycle before the run resumes.
- **A run that died `active` with no failure recorded is still refused**, as before ("is being worked on right now"). The live case is `failed` because the daemon's own watch failed the run when the session was killed; a daemon that dies *with* its session leaves the run `active` until the reclaim path (ADR-0020) fails it, and `retry` then works. Changing that refusal would be changing liveness judgement, which is not this slice's.
- **The fallback to `waitCursor` was kept.** 19c's rule — rewind a conversation park whether or not anything was consumed — is what every run already parked when this build lands depends on: their answers were consumed by a daemon that recorded no marker, and the cursor sitting on the answer is all they have.
