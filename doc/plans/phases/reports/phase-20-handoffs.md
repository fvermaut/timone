# Phase 20 — Sub-agent handoffs

> One section per sub-phase, appended in execution order, each committed with its own sub-phase's commit. Format per `process.md` stage 6.

## 20a — one computation, two renderers

**Built.** There is now exactly one place that decides what an open ticket needs from the human, and `timone status` reads it rather than deciding for itself. `ctaFor(state)` maps a ticket's state — its run or the absence of one, that run's status, stage, recorded wait and pull request, and the ticket's labels — to a `Cta`: a headline, the words that follow *"What I need from you:"*, whether the human is what it is waiting on, and the exact command when one moves it. `ctaComment(cta)` renders that onto a ticket. `timone status` renders the same value onto the terminal: its parked-run phrase, its failure block's command, and its closing line's list of tickets all come from `ctaFor` now. **The observable output of `timone status` is byte-identical to `main`'s across sixty-four rendered states** — this slice relocates a decision, it does not rewrite copy.

The contradiction R21's clause 8 forbids is now impossible rather than merely absent: the terminal and the ticket read one value, so they cannot disagree about what a ticket needs. Proven structurally, not by two strings happening to match — see the mutation probe below.

**Files touched.**

- `src/daemon/cta.ts` — created. `TicketState`, `Cta`, `ctaFor` (the computation), `ctaComment` (the ticket renderer).
- `src/daemon/cta.test.ts` — created. 25 tests: one per state, plus the whole stage graph as a table.
- `src/commands/status.ts` — `describeWait` now asks `ctaFor`; the failure block prints the CTA's command instead of building `timone retry <id>` itself; the closing line filters on the CTA's `waitingOnYou` instead of on `run.status === "parked"`. No other change.
- `src/commands/status.test.ts` — two tests added under *"one computation, two renderers"*. Nothing existing was edited: all 22 prior tests pass untouched, which is the "output unchanged" evidence.

**Decisions taken inside the slice.**

- **The file naming is right, and I would keep it.** `src/daemon/cta.ts` beside `gate-comment.ts` is where it belongs: `gate-comment.ts` is already a pure comment composer with no I/O and no adapter, and this is the same kind of thing one level up. `src/commands/status.ts` importing from `src/daemon/` is not new either — it already imports `modelFor` from `pipeline.js` and `Run` from `runs.js`. **No move is warranted; 20b–20f can write their file grants against these names.**
- **`ctaComment` lives in 20a, not 20c.** My checkbox demanded that the status line and the ticket body for one state be proven to come from one call, which is unprovable without a ticket-body renderer existing. It is a renderer — every word it emits comes off the `Cta` it is handed — so it does not put a second decision anywhere. 20c should call it and never compose a body of its own.
- **`timone status`'s wording did not change anywhere, including where it is arguably wrong.** Two states tempted me and I left both alone, deliberately, because the brief says nothing a human reads may change in this slice:
  - A run **parked at an unbuilt stage** is still listed as *"waiting on you: the next stage to be built"* and still named in the closing line's *"answer on …"*, even though nothing the human can type moves it. ADR-0024's own evidence table calls that line *truthful*, and the ticket now carries the identical words, so the two surfaces agree — which is what clause 8 asks. **Making it read "waiting:" and dropping it from the closing line is a copy change and belongs to a later slice or the delivery review**, not here.
  - A **failed** run has `waitingOnYou: false`, so the closing line still says *"nothing is waiting on you right now"* three lines under *"to pick it up from where it stopped: timone retry …"*. That is today's behaviour exactly. Flipping it to `true` would have changed the closing line, which the brief forbids. The field's docblock states the contract precisely so a later reader does not think it is an oversight.
- **`waitingOnYou: boolean` + `command?: string` rather than a discriminated union.** `standards/typescript.md` prefers unions over flag combinations, and a `CtaMove` union (`nothing` / `reply` / `reply-or-run` / `run`) is arguably the better shape. I did not build it because the two fields are genuinely independent facts — *who is waited on* and *whether anything they type moves it*, and a failed run is the state where they legitimately disagree — and because a five-variant union with one consumer is speculative generality at this size. **Listed under refactoring below.**
- **A marked ticket with no ledger run gets "nothing right now — I'll comment here when I do."** — the daemon is what moves it, on its next pass. An **unmarked** one gets *"add the `timone` label to this ticket and I'll pick it up."*, `MARK_LABEL` interpolated rather than spelled, echoing `takeover.ts`'s existing refusal wording. **Neither branch names `timone takeover`**, because 20g has not built tracker resolution yet and a CTA naming a command that refuses is worse than one naming none.
- **The retry command is built from `runId(project, ticket)`**, not from `run.id`. Identical for every run the store creates — `runId` is what makes them — and it means the command does not need a ledger row to be computed, which is what 20c will want for a ticket that has none.
- **No dependency on `pipeline.ts`.** I considered telling a park at a *built* stage from one at an unbuilt stage via `isBuilt`, so the built one could honestly say nothing is needed. It would have changed what a human reads, so it is not this slice's. Every branch keys on the run's own recorded fields instead.

## 20b — the ticket-side upsert

**Built.** The ticketing seam can now revise a standing statement on a **ticket** instead of repeating it. `upsertComment(project, number, marker, body)` replaces whatever Timone last said under `marker` by editing that comment; where it has never said it, it posts a fresh one. The GitHub implementation tells its own comment from the human's by the machine header alone — never by the author, who is the same account — so a human quoting the marker back into the thread is posted beside, never overwritten. **Nothing calls it yet**: 20c and 20d are its callers.

The seam's docblock is amended from *"Nine capabilities"* to *"Ten"*, and the widening carries its argument on the call, as that docblock demands. The argument is `upsertPullRequestComment`'s, **cited and deliberately not restated**: a CTA is the same kind of thing a preview is — a standing fact whose truth changes, reconciled every cycle — and appending it would fill a client's ticket with near-identical comments.

**Files touched.**

- `src/adapters/ticketing.ts` — `upsertComment` added to `TicketingAdapter`, between `postComment` and `applyLabel`. Its docblock names itself phase 20's widening, points at its twin for the edit-never-append argument and at ADR-0024 for why a CTA is that kind of statement, and states the identity rule implementations must follow. The interface's own docblock now says ten capabilities and *"the last two are phase 16's and phase 20's"*.
- `src/adapters/github-tickets.ts` — `GitHubTicketingAdapter.upsertComment` implemented: `gh issue view N --json comments`, find ours-and-marked, `PATCH repos/<slug>/issues/comments/<id>` or fall back to `postComment`. `ghCommentSchema.url`'s docblock corrected — it claimed `gh pr view` was the only place the numeric id surfaces, which is now false, and it records that GitHub serves both surfaces from one endpoint.
- `src/adapters/github-tickets.test.ts` — 5 tests added under `upsertComment`. Nothing existing was edited.

**Decisions taken inside the slice.**

- **It reads with `gh issue view`, not `gh pr view`.** Obvious, and a copy of the twin would have got it wrong silently — a fake runner returns canned JSON whatever the verb, so no other test in the file would have noticed. Pinned by a test of its own that fails when the verb is swapped.
- **It writes to the same REST endpoint as its twin.** `repos/<slug>/issues/comments/<id>` is not a shortcut: to GitHub a ticket comment and a pull request's conversation comment are one resource, which is why `#issuecomment-` addresses both and `commentDatabaseId` needed no change.
- **No `CTA_MARKER` is defined here.** Markers live in `ticketing.ts` beside their siblings, but a constant with no user is speculative and the plan gives the marker to 20c. **20c and 20d must define theirs in `src/adapters/ticketing.ts` — check your file grant covers it, and escalate before inventing a home for it elsewhere.**
- **A comment with no `url` throws rather than posting.** Same ruling as the twin, for a reason the twin's docblock states: posting is precisely the outcome editing exists to prevent, and here it would leave two calls to action on one ticket, one of them stale, with the machine's name on both.
- **The duplication with `upsertPullRequestComment` was left standing, deliberately.** The two methods now share a find-then-patch shape, and the identity predicate is a duplicated *decision* of the kind `standards/code-smells.md` calls out. Refactoring is deferred to the delivery review per stage 6; see below.

**Refactoring noted, deferred to the delivery review** (nothing applied): `upsertComment` and `upsertPullRequestComment` are now the same algorithm twice — read the thread, find ours-carrying-the-marker, patch it by database id or post fresh — differing only in the read command and the post fallback. **What 20c and 20d must know.**

- **The signature.** `upsertComment(project: TicketingProject, number: number, marker: string, body: string): Promise<void>` on `TicketingAdapter`. Same argument order as `upsertPullRequestComment`; `number` is the ticket number.
- **What a marker must look like.** Any stable, unique line that appears **in the body you pass**, because that is the only reason the next cycle can find what this one wrote. Follow the siblings in `src/adapters/ticketing.ts`: an emoji, a bold label, a `·`, then a clause saying who wrote it and why. It must not be a substring of another marker, and once it ships it can never change — an edited marker orphans every comment already posted under the old one, and the next cycle posts a second CTA beside the first.
- **Do not stamp the body.** The adapter calls `stampMachineComment` on both paths. `ctaComment(cta)` from 20a carries no marker, so **prepend the marker to that body yourself** and pass the same string as `marker` — the header is the adapter's business, the marker is yours.
- **The differs-from-last guard is yours, not the adapter's.** `upsertComment` edits unconditionally: handed the same body twice it issues two identical PATCHes. It does not read what it is about to overwrite for comparison, so 20c must fetch the thread (`getTicket`) and compare against the last machine comment carrying the marker before calling. This is the guard ADR-0024 calls load-bearing; **the adapter will not enforce it for you.**
- **Two `gh` calls per invocation** — a view and a post-or-patch. On a project with many open tickets that is the cost 20c's cycle pays per ticket it decides to write; the differs-from-last guard needs a read anyway, so reuse it and do not read twice.
- **The failure modes to handle.** It throws on an unparseable or unexpected `gh` payload (message carries the raw text), and it throws `…with no url, so it cannot be edited` when the comment it must edit has no permalink. Both are per-ticket; a cycle reconciling many tickets must not let one ticket's throw abandon the rest.
- **`recordingAdapter` in `poll.test.ts` cannot see you yet.** Its `upsertComment` is a conformance no-op and `WRITES` does not list it, so the "never writes to what the human wrote" test would watch you write and report nothing. Fix that in the same slice that first calls the method.
- **20d's introduction is a different call.** It is posted exactly once and never revised, so it wants `postComment` with its own marker recorded, not `upsertComment` — reaching for the upsert would make it revisable, and an introduction that rewrites itself is not an introduction. Use `getTicket` and look for your marker to decide whether it has already happened.

## 20c — the CTA is reconciled each cycle

**Built.** Every ticket the poll loop sees now carries one standing statement of where it stands, and the daemon keeps it true instead of leaving it to whoever last touched the ticket. At the end of each project's turn in a cycle the loop asks `ctaFor` what each listed ticket needs, renders it with `ctaComment` under a new `CTA_MARKER`, and **calls `upsertComment` only where that body differs from the one already on the ticket**. A ticket whose blocker closed is brought up to date because a cycle ran — not because a session remembered it — and a cycle over tickets that have not moved touches nothing at all. The mark label still bounds what Timone *does*; this changes what it *says*.

Nothing about the two answer paths, gate parsing or what a resolution looks like changed, `wayfinding` still has no `next`, and there is still exactly one place deciding what a ticket needs.

**Files touched.**

- `src/adapters/ticketing.ts` — `CTA_MARKER` added beside `PREVIEW_MARKER`, whose *kind* of marker it is: an identity to find the last statement by, not just provenance. Nothing else in the file.
- `src/daemon/poll.ts` — `reconcileCtas` (the reconciliation and its guard), `ctaBody`, `standingCta`, `saysTheSame`; `threadReaders` hoists the per-run thread memo to one reader per ticket for the project's turn, so the reconciler reads what the resume path already read; `pollProject` collects the tickets it acknowledged this cycle and calls the reconciler last. `RunThreads`'s lifetime docblock amended to say what the sharing is now keyed by and why.
- `src/daemon/poll.test.ts` — 8 tests added under *"pollOnce — the call to action is reconciled each cycle"*, the zero-writes guard first. `recordingAdapter` now records `upsertComment` and `WRITES` lists it (20b's flagged debt, paid). One pre-existing test — *"tells a young watch apart from an absence"* — read its two log lines by index and now filters for them by content; the assertions are unchanged.

**Decisions taken inside the slice.**

- **The rendered body is the comparison key, and the ticket is where it is kept.** `ctaComment(ctaFor(state))` is pure, so a body equal to the one on the ticket *is* the statement that nothing changed. No ledger record was added — `runs.ts` is outside this slice's grant, and keeping the key on the surface a human reads means the ledger and the ticket cannot disagree about what was last said.
- **The guard reads by the same rule the upsert writes by**: ours (`fromTimone`), carrying the marker, **the first** such comment — `upsertComment`'s own `find`. A guard that judged differently would compare against one comment and edit another, finding a difference every cycle for ever. That is the storm wearing the costume of a fix, and it has a test with a mutation probe of its own.
- **The comparison is by words, not bytes** (`saysTheSame` normalises CRLF and trims). The guard fails *open*: if the tracker hands a body back in a shape it was not sent in, every cycle finds a difference and rewrites the comment silently. This is the one door through which the exact fault ADR-0024 names could still arrive, and closing it costs two lines. **It cannot be fully closed by a unit test — see what 20h must know.**
- **A ticket acknowledged this cycle does not also get its standing copy this cycle.** `pickedUpComment` and `queuedComment` end on the very line the CTA is made of, so posting it under a marker seconds later is two near-identical comments in one cycle — the thing the guard prevents everywhere else. The standing copy lands on the next cycle, by which time the run has usually moved on and it says something new.

## 20e — the backlog switch

**Built.** Timone no longer speaks in a repository that has not asked it to. A per-project manifest key, `introduce_unmarked`, governs 20d's introduction, and **absent means off**: a project registered before this key existed — which is every project on disk today — receives no introductions, makes no open-ticket listing, and costs its tracker nothing at all. A project that sets it to `true` behaves exactly as 20d built it. The gate sits at the top of `introduceUnmarked`, above the listing call, so off is silence rather than a request whose answer is thrown away.

This is ADR-0024's *"the whole of the restraint"*, and PRD-02.R21's third criterion — *"a project onboarded with a backlog … no introduction is posted on any of them"* — is now the loop's default rather than something nobody had built. Onboarding is told to decide it, per project, as a question of its own with the count of the repository's open issues in front of it.

Nothing about the two answer paths changed, `wayfinding` still has no `next`, `ctaFor` is still the only place deciding what a ticket needs, and the standing call to action is still reconciled onto marked tickets only.

**Decisions taken inside the slice.**

- **`optional()`, not `default(false)`** — and this is the load-bearing choice. `z.boolean().default(false)` also makes an absent key behave as off, and it is the wrong shape here for two reasons. It would make `ProjectConfig.introduce_unmarked` non-optional, so **every write of the manifest through `serializeManifest` would stamp `introduce_unmarked: false` onto every project in the file** — an opinion arriving in entries nobody edited, on the next `projects add` anyone runs, which is the exact "Timone acquires an opinion about repositories it has not been given" the ADR's consequences warn about. And it would break three pre-existing tests that compare a parsed entry against the literal that produced it. Probed rather than argued: `.default(false)` fails **5** tests, three of them 20e's and two of them older than this phase.
- **The key is a top-level project field, not a member of `bindings`.** `bindings` answers *which adapter*; this answers *whether to speak*. The existing docblock on `PollDeps.previews` states that distinction outright — *"the binding says which adapter, never whether to have one at all"* — and putting a behavioural switch in there would contradict a sentence already in the file.
- **The gate is `!== true`, and it is the first statement in the function**, above the `deps` destructuring as well as above the listing. `=== false` is the tempting spelling and it is the wrong default: it makes an absent key mean *on*. Driven red by exactly that mutation.
- **`introducing()` is a transformer over a manifest, not a second builder.** `manifestWith` keeps producing an entry with no switch, so the 60-odd tests that are not about introductions go on asserting against a project that has never thought about this — which is what a default off has to mean. Had I put the switch into `manifestWith` itself, the default would have been a default in name only and my own default-off case would have been the one fixture in the file that disagreed with every other.
- **20d's tests were re-pointed, not rewritten.** Nine call sites changed from `manifestWith(…)` to `introducing(manifestWith(…))` and nothing else in those tests moved: no assertion, no fixture, no expectation. They assert what an *introducing* project does, which is what they always meant; before this slice there was no other kind. The three in that block that assert an absence (no run created, a marked ticket untouched, the ledger and not the thread) were re-pointed too, deliberately — left on a switched-off project they would have passed vacuously, asserting the absence of a behaviour that could not have happened.
- **`twoListings` records the project on `postComment`.** One field on the fake's call record, so the two-project case can assert *which* repository was spoken to rather than only how many comments there were. Existing assertions in that block filter or compare empty arrays, so none of them sees it.
- **No `PollResult` field, no log line for a project that says nothing.** 20c and 20d both ruled that an introduction is not a run; a *declined* introduction is less than that. A silent project produces no output at all, which is what makes `grep -c '^hello '` still mean what 20d's handoff says it means.

## 20f — the map becomes first-class

**Built.** A wayfinder map is now a ticket the machine listens to. It carries the `timone` mark from the moment it is charted, enters a stage of its own — `charting`, a fifth wayfinder kind beside the four decision types — and its standing call to action tracks its own state: while its questions are open it says *"nothing right now — I'll come back here when the last one is closed"* and **starts nothing whatever anybody writes on it**; once the closing session empties the frontier it says *"say go ahead here and I'll write the specification this map has been finding its way to"*, and a plain comment agreeing **runs stage 3 on the map's own run**, holding the whole project until the specification is committed. That is the sentence `ivtrends` #1 needed on 2026-08-13 and the answer fvermaut wrote that nothing was listening for.

**`wayfinding` still has no `next`, and that is asserted directly as its own test.** The map's `next` is on `charting` and nowhere else — a PRD written off one decision ticket's answer is the fault that clause exists to prevent, and adding a stage beside it is exactly the move that breaks it by accident. Nothing about the two answer paths changed: no new way to answer, no change to gate parsing, no change to what a resolution looks like. The go-ahead is an ordinary written answer read by the same `writtenAnswer` every other conversation is read by. And there is still exactly one place deciding what a ticket needs — the map's two calls to action come out of 20a's `ctaFor`, off the run, so `timone status` and the ticket cannot disagree about them.

**Decisions taken inside the slice.**

- **The stage is called `charting`, and it is one stage rather than two.** It surfaces in `timone status` (`ivtrends #1 (charting)`) and it is the skill's own verb for the effort. One stage with two waits, rather than an "open" stage and a "clear" stage, because the ledger already has a place for *what a run is waiting on* and inventing a second stage to say it would put the same fact in two places.
- **The frontier's emptiness is a label, and the run's wait is what the call to action reads.** These are two decisions and both are load-bearing. A label because the session that closes the last decision ticket works the tracker, not the ledger, and because a human reading the map can see it. But `ctaFor` must **not** read it: `timone status` has no tracker and passes no labels, so a labels-keyed branch would have made the terminal and the ticket disagree about the map — reintroducing the exact fault R21's clause 8 forbids and 20a closed. So the poll loop translates the label into the run's wait once (`openGoAheads`), and both surfaces read the run.
- **A map being worked parks with no wait kind.** That state already means *"stopped, and not waiting on a human"*, which is precisely true of a map working its list — and it is what lets `ctaFor` tell the two map states apart from run facts alone. It cost one guard in `resolveWait`, because the existing no-kind branch means "a stage that could not run" and would otherwise resume the map into a session every cycle.
- **The map's stop posts nothing.** Every other conversation stage posts the invitation; the map's question is not owed yet, and a question on a ticket nobody can answer is this phase's own fault inverted. Its standing call to action — reconciled every cycle by 20c — is the whole of what the map says, which is also why the flip needs no comment of its own: the same reconciler writes it.
- **The wait is opened at the machine's last word** (`waitCursorFrom`), not at the moment the cycle runs. A map is a ticket people talk on for weeks, and everything written before the way was clear was written about something else — it cannot agree to a question nobody had asked. The other half is `waitCursorFrom`'s own reason: a human who answers the closing summary within the minute must not land past their own answer. **This is why the skill's closing posts the route summary before applying the label**, and the skill says so.
- **The go-ahead advances rather than re-entering the stage.** Everywhere else a written answer re-runs the same stage, because that stage must judge whether the answer settles its question. Here nothing runs at the stage at all, and the human's words are carried into the requirements session as its feedback — so the PRD session reads the agreement rather than being told one happened. It also means **no prompt was needed for `charting`**, and `src/daemon/prompts.ts` (outside the grant) was never touched.
- **The frontier is re-checked at the branch that starts a build.** Two copies of one clause, deliberately: the wait is opened only when the frontier is empty, but a map can grow a question back afterwards, and the branch that spends a project for hours is the one worth guarding twice.
- **Opening the wait is one-way.** A reopened frontier leaves the wait standing rather than withdrawing a question the human may be halfway through answering; nothing starts meanwhile, because of the re-check above. The skill tells the closing session to put the working line back in the body.
- **Neither map call to action names a command.** `timone takeover` refuses `charting` by name (*"a stage I can't hold a conversation for yet"*) because the stage has no prompt, and 20a's rule stands: a call to action naming a command that refuses is worse than one naming none.
- **The graph now admits a stage that is built and spawns nothing.** `built: false` was the only way to declare no model, and it would have made the daemon park the map with *"the next stage to be built"* — a lie. `spawns: false` says the true thing, and keeps `modelFor("charting")` undefined so nothing can silently take the runtime's default.

## 20g — takeover resolves from the tracker

**Built.** `timone takeover` no longer needs the ledger's permission to have heard of a ticket. For an **open** ticket with no run, it reads the tracker, works out where that ticket enters the pipeline from the labels the tracker holds, **creates the run**, and opens the session — the stage-2 conversation for a wayfinder decision ticket charted straight through `gh`, triage for a request nobody has classified. The sentence PRD-02.R20 has failed on since phase 18 — *"I'm not working on X. Reopen it if it still needs something from me."*) and one that **does not exist** (*"There's no ticket #99 on scratch-app. Check the number — I can only pick up something that exists."*). Nothing about the two answer paths changed: no new way to answer, no change to gate parsing, no change to what a resolution looks like. `wayfinding` still has no `next`. `ctaFor` is still the only place deciding what a ticket needs — **this slice does not touch `cta.ts`**; see the decisions.

**Decisions taken inside the slice.**

- **The mark label is not applied, and this is the load-bearing choice.** Marking the ticket would make the tracker and the ledger agree, and it is what the retired refusal told the human to do by hand. It is refused for a reason that is fatal on its own: **`gh issue edit --add-label` fails when the label does not exist**, and a repository with no `timone` label is precisely the case ADR-0024 cites (*"marking a ticket there fails silently, and then `takeover` refuses — so there is no way in whatsoever"*). A takeover that applied the label would fail on the one repository it exists to rescue. The ADR's own wording is also narrow — *"creates the run on demand"*, with marking at creation kept as the daemon's route — so this adds nothing beside it. **The cost is real and is reported as an escalation below**: an enrolled ticket that is still unmarked is invisible to the two listing-driven passes in `pollProject`.
- **The new run is left in the state the daemon's own pickup would have left it in at that stage, and no other.** That is the whole rule (`settle`), and it is what keeps a takeover-created run resumable by machinery that already exists:
  - a stage whose wait is a **conversation** (`wayfinding`) is **parked** on one, exactly as `openConversation` parks it — so the daemon resumes it off the `✅ Agreed` record the session posts, or off a written answer, by the path every takeover has always used. **The invitation is not posted**: it would be a question typed at somebody already sitting in the conversation, and `holdMap`'s reasoning about the third comment saying one sentence applies verbatim.
  - anything else (`triage`) keeps the `picked-up` that `register` just produced, with its stage written down. It is **not** waiting on a human, and `park`ing it with a conversation wait would put that lie in the ledger *and* on the ticket, since `ctaFor` reads the same fields — and would contradict the graph, where `waitFor("triage")` is `none`.
- **The wait cursor is `outcomeCursorFrom(thread)` — the newest comment of any kind — not `waitCursorFrom`.** A conversation opened *now* cannot be answered by anything already on the ticket. `waitCursorFrom` answers "when did the machine last speak", which on a ticket where the human wrote last would put the cursor **before** their old comment and have the next cycle resume this run behind the session they are sitting in. Same reasoning the spawner gives for taking `laterOf` its two candidates.
- **A stage no conversation exists for is refused *before* anything is written down.** `charting` and `research` are not in `PROMPTED_STAGES`; enrolling first and refusing after would leave a run on the map carrying a wait **nobody has asked for**, which is ADR-0024's own fault inverted, and 20f's instruction to exclude the map is honoured at the earliest point rather than the latest. One test asserts the map gets no run *and* that its thread is never even read.
- **A ticket enrolled behind a run holding its project is queued and told so**, rather than opening a second session — `register` produces `queued` there, and `queued → parked` is not a transition the ledger allows, so this is a real guard and not a nicety. The queue sentence is now one function called from both places instead of two copies.
- **Closed and absent are told apart by asking the tracker again**, on the refusal path only. One sentence for both would leave the human checking the wrong thing; a `getTicket` that throws *is* the answer, and it costs nothing on any path that succeeds.
- **`cta.ts` was not touched**, though the grant allowed it. 20a reserved the no-run branch for exactly this slice, and I did not take it, for three reasons. The **marked** no-run branch is honest already (the daemon moves it, on its next pass) and 20a's rule stands that a CTA should not name a command where nothing is needed. The **unmarked** no-run branch has **no renderer today** — `reconcileCtas` walks the marked listing and `timone status` walks the ledger, so nothing anywhere would print a changed word — which means editing it could not close R21 clause 1 for those tickets even in principle. And naming the command correctly there would require excluding maps and `research`, i.e. duplicating this command's entry-stage resolution inside `src/daemon/`, which is a second place deciding. **The open question 20d and 20e both flagged — whether an unmarked ticket gets a standing CTA at all — is fvermaut's, and this slice deliberately does not half-answer it.**
- **A tracker call that throws still propagates**, as `getTicket` already did in this command before this slice. The failure surface is wider now (two more calls, one of them on the refusal path), and it is unchanged in kind; the lock is released either way, since `withStateLock` releases in a `finally`.
